## 一、总览

本系统的提示词不是散落的字符串，而是一套**分层模板库**：从"理解用户"到"生成代码"再到"修复代码"，每一层都有固定模板，并由统一的规则片段注入约束。

| 编号 | 模板 | 作用 | 实现位置 |
|---|---|---|---|
| P1 | 意图解析模板 | 中文需求 → 结构化参数 | `intent.py::_build_parse_prompt` |
| P2 | 多步规划模板 | 一句话 → 多个子任务 | `planner.py::_build_prompt` |
| P3 | 代码生成模板 | 参数 → 可运行 GEE 代码 | `codegen.py::_build_prompt` |
| P4 | 代码修复模板 | 报错 + 代码 → 修复后代码 | `codegen.py::fix_code` |
| P5 | 对话问答模板 | 咨询模式专家问答 | `ask.py` |
| R1 | 资源预算规则 | 约束计算规模，防超时/内存超限 | `codegen.py::_RESOURCE_RULES` |
| R2 | 任务口径规则 | 四类任务的分析口径固化 | `codegen.py::_TASK_CALIBER` |
| R3 | 知识注入片段 | 检索数据集并注入 | `knowledge.py::build_knowledge_note` |
| R4 | 用户偏好片段 | 按用户注入偏好与风格 | `preferences.py::build_preference_note` |
| R5 | 日期基准规则 | 动态生成，避免年份写死 | `daterange.py::month_range_rule` |

**设计原则**：模板负责"框架"，规则片段负责"约束"。规则片段可被多个模板复用（如 R1 同时注入 P3 与 P4），修改一处即全局生效。

## 二、P1 · 意图解析模板

**输入**：用户自然语言 + 已确认的参数（多轮澄清用）
**输出**：严格 JSON

```
你是卫星遥感分析意图解析器。把用户的中文需求解析为 JSON，只输出 JSON 本身，
不要任何解释文字、不要 markdown 代码块围栏。
```

用户消息模板：

```
请解析下面的用户需求，输出如下结构的 JSON：
{"task_type": string|null, "region": string|null, "start_date": string|null,
 "end_date": string|null, "cloud_threshold": number|null}

字段规则：
- task_type 只能是以下之一或 null：ndvi(植被指数)、water(水体提取)、
  classification(地表分类)、change_detection(时序变化检测)。
- region 只填**地名本身**（如 太湖流域、洞庭湖、北京市），或 null。
  不要带动词、时间词、疑问词。
- start_date/end_date 为 YYYY-MM-DD 或 null。{R5 注入}
- cloud_threshold 是云量阈值(0-100 数字)，用户没提就 null。
只填能从用户话里确定的值，不确定一律填 null。

已确认的参数（保持不变，除非用户新话里明确修改）：{partial JSON}

用户需求：{text}
```

**关键设计点**

| 点 | 说明 |
|---|---|
| `temperature = 0.0` + `response_format = json_object` | 结构化输出要稳定，不允许发散 |
| region 抽取的显式约束 | 实测「看看鄱阳湖现在的水域范围」被解析成 `region="看看鄱阳湖"`（动词混进地名）；「太湖的水面面积最近有啥变化」region 丢空。补了"先剥掉动词与时间词"后，13 条用例 3 轮稳定 100% |
| `partial` 合并语义 | 多轮澄清时只覆盖非空新值，已确认参数保持不变 |
| 不确定填 null 而非猜测 | 兜底与默认值统一由 `_summarize` 在服务端处理，模型不承担默认值逻辑 |

## 三、P2 · 多步规划模板

**输入**：一句话需求
**输出**：`{multi, tasks[]}`

```
你是卫星遥感分析任务规划器。判断用户的一句话需求是单一分析目标还是多个独立目标，
若含多个独立目标，拆解为多个子任务。只输出 JSON 本身，不要任何解释、不要 markdown 围栏。
```

```
请分析下面这句用户需求，输出 JSON：
{"multi": boolean, "tasks": [{"task_type": string, "region": string|null,
 "start_date": string|null, "end_date": string|null, "cloud_threshold": number|null}]}

规则：
- 如果需求只含一个分析目标，multi=false，tasks 为空数组 []。
- 如果含多个独立目标（例如同时要「水体提取」和「植被分析」），multi=true，
  tasks 里每个目标一个子任务。
- task_type 只能是：ndvi、water、classification、change_detection。
- region 是分析区域；start_date/end_date 为 YYYY-MM-DD 或 null（{R5 注入}）。
- cloud_threshold 用户没提就 null。
只输出 JSON。

用户需求：{text}
```

**关键设计点**：模型给出的 `tasks` 会在服务端**二次校验** —— 非法 task_type 丢弃、拆解结果不足 2 条时 `multi` 强制回落 `false`。模型不拥有最终判定权。

## 四、P3 · 代码生成模板（核心）

**输入**：`AnalysisRequest`（任务类型 / 区域 / 时间 / 云量）+ 用户 ID
**输出**：纯 Python 代码，无围栏

```
你是资深卫星遥感与 Google Earth Engine 专家，负责把自然语言需求转成可运行的 Python 代码。
```

用户消息由 6 段拼装，顺序固定：

```
请生成一段 Google Earth Engine（Python API，模块名 ee）分析代码。
任务类型：{TASK_LABELS}
分析区域：{region}
{坐标块}
时间范围：{start_date} ~ {end_date}
云量阈值：{cloud_threshold}%
{R3 知识注入}
{R4 偏好注入}
{R1 资源预算规则}
{R2 任务口径规则}
要求：
1. 只输出 Python 代码本身，不要任何解释文字，不要 markdown 代码块围栏。
2. 第一行 import ee（ee 已由沙箱预初始化，无需再调用 ee.Initialize()）。
3. 用 ee.Geometry.Rectangle 或 ee.Geometry.Polygon 定义 AOI（用上面给的坐标）。
4. 使用 Sentinel-2 或 Landsat 数据，按云量阈值筛选。
5. 计算并 print 关键统计结果。
6. 必须用 WB 报告器上报可视化结果，否则前端拿不到地图与图表：
   · WB.add_image_layer('图层名', image, vis_params, legend=[...])  —— 上报栅格图层
   · WB.add_feature_layer('图层名', featureCollection)              —— 上报矢量图层
   · WB.add_chart('图表标题', labels=[...], series=[...], kind='line'|'bar'|'pie')
   · WB.stat('指标名', 数值)                                        —— 上报关键统计值
7. 可用上下文变量：region、start_date、end_date、cloud_threshold。
8. 代码风格：{profile['code_style']}
```

**坐标块的两种形态**

| 情形 | 注入内容 |
|---|---|
| 区域在内置表里 | `区域中心坐标：经度 X、纬度 Y。AOI 请以该点为中心，用 [x-0.25, y-0.25] ~ [x+0.25, y+0.25] 构造 ee.Geometry.Rectangle，不要自行猜测更大范围。` |
| 不在内置表 | `该区域没有内置中心坐标，请自行给出一个合理的经纬度，并保证 AOI 不超过 0.5°×0.5°。` |

把坐标算好交给模型，而不是让模型自己猜 —— 这是"小 AOI 硬约束"能真正落地的前提。

## 五、R1 · 资源预算规则（硬约束）

> 真实 GEE 在 Google 服务端计算，AOI 一大、分辨率一细就会撞 `User memory limit exceeded` 或直接超时。这些约束写死在提示词里，比事后让模型"自己修"可靠得多。

| 条 | 规则 | 违反后果 |
|---|---|---|
| a | AOI ≤ 0.5°×0.5°（约 50km×50km），以给定中心展开，禁止跨省框选 | 内存超限 |
| b | 禁止对全域 `.reproject()`；需降采样就把 `scale` 写大（≥250） | 内存超限 |
| c | `reduceRegion` 必须带 `bestEffort=True, tileScale=16, scale>=250, maxPixels=1e9` | 超时或报错 |
| d | 控量只能在**时间分组内部**做：逐月取 `.sort('CLOUDY_PIXEL_PERCENTAGE').limit(4)`；**严禁**对全年集合整体 `.limit(24)` | 按时间截断 → 后半年无数据、曲线出现一串 0 |
| e | 逐月曲线服务端一次性聚合；**禁止** for 循环里反复 `getInfo()` | 12 次往返必超时 |
| f | 逐月统计**不要硬套云量阈值**：长三角 4/6 月常年整月无低云影像，硬筛会让该月为空、`median()` 报 `No band named` | 该月统计崩溃 |
| g | 逐月必须有兜底：`ee.Algorithms.If(size().gt(0), 统计值, None)`；**禁止**把 None 静默写成 0 | 伪造出错误曲线 |
| h | 只 `.select()` 计算必需波段，不要整幅多波段全参与运算 | 内存超限 |
| i | `.map()` 加工后必须 `copyProperties` 带上 **两个**属性：`system:time_start` 与 `CLOUDY_PIXEL_PERCENTAGE` | 漏前者→`filterDate` 返回空集合；漏后者→`.sort()` 静默失效（**不报错**，选出来是随机几景） |
| j | **None 属性会被省略**：属性值为 None 时 `getInfo()` 的 properties 里**根本不会有这个键**，读属性必须 `.get('k')`，不能 `['k']` | 第一个空月直接 KeyError 掉整段分析 |
| k | **Image 与 ImageCollection 方法不通用**：`ee.Image` 没有 `.mode()`（那是 ImageCollection 的）；`.select()`/`.clip()` 之后仍是 Image | `AttributeError: 'Image' object has no attribute 'mode'` |

**规则 i / j / k 都来自真实事故**，不是预防性设计：

- 规则 j：2026-09-17 变化检测任务写成 `f['properties']['ndvi']`，鄱阳湖存在空月，**连续 3 次重试全部 KeyError**，直接导致量化指标不达标；
- 规则 k：分类任务写成 `img.select('label').mode()`，**3 次错误信息逐字相同**（说明修复未产生任何改动），根因是模型对 GEE API 的幻觉。

## 六、R2 · 任务口径规则

> **必须固化**：口径不固定，同一请求两次结果会差到无法解释。

### ndvi · 植被指数

| 条 | 规则 |
|---|---|
| 1 | 波段：只需 `.select(['B4', 'B8', 'SCL'])` |
| 2 | **必须做像元级掩膜**，排除 SCL 的：3（云影）、8/9（云）、10（卷云）、11（雪）、**6（水体）** |
| 3 | 掩膜写法须同时含 SCL 类别 + 反射率有效性（`B8>0` 且 `B4>0`） |
| 4 | 返回时 `copyProperties` 带 `['system:time_start', 'CLOUDY_PIXEL_PERCENTAGE']` |
| 5 | 逐月排序**只能按云量**，严禁按时间 |

**为什么必须排除水体**（实测，太湖流域 2024，AOI 0.5°×0.5°、其中约 88% 是水面，同一份数据同一段代码逻辑）：

| 口径 | 全年均值 | 逐月范围 | 曲线形态 |
|---|---|---|---|
| 不掩膜水体 | **-0.12** | -0.21 ~ -0.01 | 几乎无季节变化 |
| 掩膜水体 | **+0.52** | 0.35 → 0.60（8月峰值）→ 0.39 | 清晰物候曲线 |

两者差 **0.64**，且后者才符合"植被指数"的语义。

**为什么必须加反射率有效性**：S2_SR 无效像元填充值是 0，`B8=0` 时 NDVI 恰好算成 -1，最小值统计出现理论边界值。加上后 `min` 由 -1 恢复正常，而 `mean`/`max` 完全不变（说明只清掉无效填充值，没误伤有效像元）。

### water · 水体提取

| 条 | 规则 |
|---|---|
| 1 | MNDWI 判水体：`normalizedDifference(['B3','B11'])`（Sentinel-2）；Landsat 用 `['green','swir1']` |
| 2 | 先掩膜云与云影（SCL 的 3/8/9/10/11），再按 MNDWI > 0 提取 |
| 3 | **面积统计必须用真实面积加权**（`multiply(ee.Image.pixelArea()).divide(1e6)`），不是像元计数 |
| 4 | 逐月按 `sort('CLOUDY_PIXEL_PERCENTAGE').limit(6)`；无有效影像的月份返回 None，**不要写 0**（0 会被当成"水体面积为 0"） |

### classification · 地表分类

| 条 | 规则 |
|---|---|
| 1 | 优先用现成分类产品：Dynamic World（`GOOGLE/DYNAMICWORLD/V1`）或 ESA WorldCover（`ESA/WorldCover/v200`），**不要自己训分类器** |
| 2 | Dynamic World 按 label 取众数合成；统计面积占比用 pixelArea 加权 |
| 3 | 逐月/逐年对比口径必须一致，并在图表标题写明产品名 |

### change_detection · 时序变化检测

| 条 | 规则 |
|---|---|
| 1 | 必须锁定两个时段，且**口径完全一致**（同一传感器、同一波段组合、同一合成方法、同一掩膜规则） |
| 2 | 用 NDVI（或 NDWI）差值法：`delta = later.subtract(earlier)`；对 delta 做阈值划分（如 ±0.1）并统计各类型面积 |
| 3 | 两个时段都要各自做云掩膜与兜底，避免某段无数据被误判为"变化" |

## 七、P4 · 代码修复模板

**输入**：原代码 + 错误信息 + 可选强提醒
**输出**：修复后的完整代码

```
下面这段 GEE Python 代码执行报错，请修复后只输出完整可运行的 Python 代码，不要任何解释。
修复要求：不要调用 ee.Initialize()（沙箱已预初始化）；
继续用 WB.add_image_layer / WB.add_feature_layer / WB.add_chart 上报结果
（至少要有一个 WB.add_image_layer 和一次 WB.stat）。
【严禁改变分析口径】只修导致报错的地方，不要改动：掩膜规则（哪些 SCL 类别被排除，
尤其水体是否被排除）、排序方式（必须仍为 sort('CLOUDY_PIXEL_PERCENTAGE')）、统计方法。
口径一变，同一请求前后两次的结果就不可比了。
{hint}
{note}
{R1 资源预算规则}
失败信息：
{summarize_error(error, code)}

代码：
{code}
```

**三类动态 `hint`（按错误分类选择）**

| 分类 | hint |
|---|---|
| `timeout` | "本次是【执行超时】，说明计算量过大。修复请**做减法而非加法**：AOI 缩到 0.25°×0.25°、scale 提到 500、影像 `.limit(12)`、去掉一切 reproject/裁剪/逐月循环" |
| 内存超限（msg 含 memory/maxpixels） | "本次是【Earth Engine 内存超限】，降低单次计算规模：缩小 AOI、scale 提到 500、tileScale=16、bestEffort=True、只 select 必需波段" |
| 其它 | "保持原有分析意图，修正导致报错的具体调用" |

**为什么超时要明确说"做减法"**：大模型的默认倾向是继续加代码（加波段、加精度），越修越慢。不给减法指令就会死循环。

**`note` 参数**：用于处理"上一轮修了等于没修"。编排层检测到修复后代码与上次**逐字相同**时，下一轮注入强提醒：

```
⚠ 重要：你上一轮返回的代码与再上一轮**完全相同**，等于没有修复，
所以这一次的报错和上一次逐字一致。这一轮必须**真正产生改动**：
把报错涉及的每个方法逐个核对是否真实存在于对应对象上；不确定就换成等价的合法写法。
例如求众数：ee.Image 没有 .mode()，应写 image.reduce(ee.Reducer.mode())，
或对 ImageCollection 调用 .mode()。
```

> **教训**：「修了没修好」和「修复根本没发生」是两件事。三次错误逐字相同是后者的特征。凡是"自动重试"的地方都该判断"这次和上次有没有区别"。

## 八、`summarize_error`：给模型的位置信息

修复模板里的 `{summarize_error(error, code)}` 不是简单回传报错文本，而是**带位置的结构化摘要**：

| 组成 | 说明 |
|---|---|
| 行号 | 从 traceback 里抠出 `<gee_code>, line N` |
| 该行源码 | 把出错那一行的实际代码贴出来 |
| traceback 尾部 | 保留调用链上下文 |
| 回调提示 | 出错行是 `.map()` / `.iterate()` 调用时，**明说位置是调用点而非缺陷点**，并把被 map 的函数体完整抠出来 |

**为什么需要"回调提示"**：实测分类任务的 traceback 把 `<gee_code>` 帧定在 `ee.List(months).map(monthly_class_stats)` —— 而**这一行本身完全正确**，真正缺陷在被 `.map()` 的函数体里（回调中抛的异常，行号会指向调用点）。只给"第 N 行"，等于把模型引去改一行没问题的代码。

> **通则**：给出位置时必须带上这条限定，否则"更精确的位置信息"反而会把模型带偏。

## 九、R3 · 知识注入片段

```
可参考的 GEE 数据集（按相关度排序，请优先选用合适者）：
1. {name} — ee_id: {ee_id}（{resolution}，{desc}）
2. ...
```

在代码生成时按"任务类型 + 区域"检索语料库，取 top-3 注入。无命中时返回空串（该段整体不出现，避免出现空的标题行）。语料库内容见 `docs/RAG语料库.md`。

## 十、R4 · 用户偏好片段

```
用户分析偏好（请尽量遵循）：
- 优先使用 Sentinel-2 数据（COPERNICUS/S2_SR_HARMONIZED）
- {用户自由文本指令}
```

**注入链路**（后台线程拿不到请求上下文，用户身份必须显式传递）：

```
submit → _run(tid, req, user_id) → run_analysis(req, user_id)
       → state["user_id"] → generate_code(req, user_id) → build_preference_note(user_id)
```

若不在链路上显式传 `user_id`，会串用别人的自定义指令。

**助手画像（Agent Profiles）**：3 种画像各自定义 `ask_style` 与 `code_style`，其中 `code_style` 注入 P3 第 8 条。

| 画像 | 代码风格注入 |
|---|---|
| 分析师（默认） | 代码结构清晰、注释精炼，关键步骤用中文注释说明 |
| 导师 | 代码注释详细，每一步都解释原理与参数含义，适合学习理解 |
| 极简 | 代码尽量精简，注释只写最必要的部分 |

## 十一、R5 · 日期基准规则

```
若用户只说了月份区间（如 6-8 月），补全为最近一个已经完整过去的对应月份区间，
不要补成未来的日期（今天是 {today_iso()}）
```

**为什么返回整句话而不是词片段**：该规则在 intent 与 planner 两处提示词里出现，若让调用方各自拼接前置从句，很容易拼成"只说了月份区间就若用户只说了月份区间（如 6-8 月）…"这种重复句。

**为什么措辞不含具体年份**：历史上这里写死"补全为 2025 年的完整日期"，到了 2026 年就成了错误基准（实测「6-8 月」被补成 2025-06-01）。改成让模型**按今天自己推算**，规则就永久有效。

> **最难查的一类 bug 是兜底默认值**：大模型对模糊时间（"现在"）返回 `null` 是**正确**行为，却会被 `or "2024-01-01"` 静态兜底钉死在 2024。查"时间不对"的问题要先看兜底值，不要先怀疑模型。

## 十三、维护约定

| 约定 | 理由 |
|---|---|
| 改提示词后必须跑 `tools/eval_metrics.py` | 意图识别是压线指标（目标 90%，曾跑出 84.6%），提示词一改就可能掉线 |
| 新发现的 GEE 陷阱一律加进 `_RESOURCE_RULES` | 事后让模型"自己修"不如事前写死 |
| 不得在提示词里写死年份/日期 | 加任何默认日期后跑 `tools/test_no_stale_year.py`（22 项守卫） |
| 任务口径变更必须同步更新本文档 | 口径是结果可复现性的基础，文档与代码不同步会让复现失效 |
| 兜底代码 `_fallback_code` 必须遵守同一套规则 | 无 key 时走的兜底路径，若不遵守 R1/R2，离线演示结果与真实链路不一致 |
