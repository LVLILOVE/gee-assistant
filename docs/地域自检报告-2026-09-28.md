## 一、为什么这个结论不是"看着像"

截图肉眼看只能判断"大概是那个地方"，不足以支撑结论。所以判据全部落在坐标计算上，且**每一层都有独立证据**：

| 层 | 判据 | 证伪的是什么 |
|---|---|---|
| 接口 | 任务回显的 `region` 必须等于请求的 `region` | "参数静默走默认值" |
| 接口 | 栅格图层 bbox 必须**包含**后端解析出的区域中心 | "区域名解析成了别的坐标" |
| 接口 | bbox 必须落在中国境内 | "退化成全球/默认视图" |
| 浏览器 | 底图瓦片编号反投影出的画布中心，距请求区域中心的距离 | "前端把地图画到了别处" |
| 浏览器 | 该距离必须**小于**到对照集里任何其它地点的距离 | "其实是另一个很近的地方"（近邻混淆） |
| 人工 | 底图瓦片上的地名标注 | 瓦片商数据，不是被测产品自己的数据，构成独立审计线索 |

**对照集**：870 个地点（业务库 406 + 坐标簿 464），比只验"落点在期望区域内"强得多——后者会漏掉"返回了隔壁那座山"。

**地图中心怎么量**：`map.getCenter()` 走不通（Vite 构建没有全局 `L`，Leaflet 1.x 也不把实例挂到容器元素上）。改成抓 `/api/basemap/{z}/{x}/{y}` 瓦片，用 Web Mercator 反投影，再把瓦片在**页面上的实测像素位置**与画布中心的偏移折算进去。这条路径不依赖任何前端内部结构。

## 三、发现并修复的缺陷：模型擅自缩小分析范围

### 现象

`广州市` 请求的区域库范围是 **0.70°×0.70°**，模型生成的代码却是：

```python
aoi = ee.Geometry.Rectangle([113.0100, 22.8800, 113.5100, 23.3800])   # 0.50°×0.50°
```

**中心照抄对了，范围被缩小了**，而且缩到的正好是某个整数上限。这类偏差在 bbox 判据上**完全看不出来**（bbox 仍然包含中心、仍在广州市），只有去读生成代码才会暴露。

### 根因（已用铁证确认）

提示词里两条 AOI 指令**自相矛盾**：

- 注入的矩形范围 —— 区域库按区域类型给 `half`，省域是 2.60°；
- `_RESOURCE_RULES` 的资源硬约束 —— "AOI 必须 ≤0.5°×0.5°"。

模型不一致地自行折中，5 个样本里 1 个选了上限值。复现 `_build_prompt()` 确认注入本身是正确的，问题出在两条规则打架。

### 修法分两半

**① 提示词（消除矛盾）**

- `_RESOURCE_RULES` 规则 a 改为"**若上面已给出矩形范围就严格照抄**，本条的 0.5° 上限**不适用于**已注入的范围"，并说明省域/大流域本来就该 >0.5°（按 0.5° 裁掉会让"山西省植被"只统计到省会周边一小块）。
- 要求 3 从"用 `Rectangle` 或 `Polygon`"收紧为"用 `Rectangle`，且**逐字照抄那四个数**"。
- `fix_code` 提示加"**AOI 的中心坐标绝对不能移动**"。

**② 生成后守卫 `enforce_aoi(code, region, *, allow_shrink=False)`**

解析生成代码里的 `Rectangle([...])` 与区域库范围比对，偏离即替换。策略是**中心不可协商、尺寸可协商**：

| 情况 | 处理 |
|---|---|
| 中心偏 > 0.02°(≈2 km) | 一律替换（"分析到别处"那一类 bug） |
| 尺寸不符，`allow_shrink=False` | 替换 |
| 尺寸偏大，`allow_shrink=True` | 仍替换（放大只会更慢） |
| 尺寸偏小，`allow_shrink=True` | **保留**（超时/内存超限时缩小是合法缓解） |
| 区域解析不出 / 无字面量矩形 | 一个字都不改（运行时解析也合法） |

`allow_shrink` 由错误类型决定：只有 `category=="timeout"` 或 message 含 memory/maxpixels 才放开。**不能一律强制恢复**——省域任务超时后把 2.6° 拽回去只会再超时一次，永远收敛不了。

### 生产验证（同一区域前后对比）

| | 修复前 | 修复后 |
|---|---|---|
| AOI 边长 | 0.500°（被缩过） | **0.700°**（=期望值） |
| 重试次数 | 2 次 | **1 次**（一次成功） |

> 守卫日志未触发 —— 提示词修好后模型直接照抄了，这是更好的结果。守卫本身的正确性由单测保证（H 段 19 项，含**反向断言**"省域 2.6° 视为合规"，防止守卫退化成"一律压到 0.5°"）。

## 五、发现但**尚未修复**的缺陷：历史任务的 NDVI 图层会静默消失

这是本次复验新查出来的，性质与上面的定位问题**无关**，但同样回答"地图匹配不上"这个疑问。

### 现象

重新打开几天前跑的任务，地图上**只有底图，没有 NDVI 色块**，也没有任何提示。

### 证据链

1. 服务端日志里 `/api/tile/` 请求 **87 次全部 400**，零成功（底图 `/api/basemap/` 全部 200）。
2. 直连上游 GEE 查证，返回的不是 400 而是：

   ```
   HTTP 401
   {"error":{"code":401,"message":"Invalid token: 66298013e7e9…（此处截断）",
             "status":"UNAUTHENTICATED"}}
   ```

   > 令牌值已在提交前截断：它虽然已被 GEE 判为 `Invalid`（不构成有效凭据），
   > 但**报告里不放完整的令牌串**是本仓库的既定规矩
   > （发布审计时曾因报告里带活密钥而返工过一次）。

3. 日志里失败的 8 个 mapid，与这 5 个任务存下来的 8 个栅格图层 **一一对应**（我逐条比对过，不是推测）。

### 原因

任务把 GEE 返回的 `tile_url` 原样存进库，而这个 URL 里嵌着**短期有效的 map 令牌**。任务跑完几天后令牌失效，重新打开时瓦片就再也拉不到了。

### 为什么这是缺陷（而不是"本来就该这样"）

失效本身是 GEE 的机制，但**产品对此完全静默**：

- 前端 `MapPanel` 的 `tileWarn` **只在瓦片模板解析不出来时**才置位；瓦片请求失败（400）不设任何提示。
- 没有任何 `tileerror` 监听。
- 结果：用户看到的是一张没有色块的底图，**无法区分"没有数据"、"图层过期"和"分析错了地方"** —— 而最后一种正是用户会直接得出的结论。

这条与本项目一贯的"不静默失败"原则冲突（同一批改动里的 `wb.notes` 上浮、AOI 守卫，针对的都是这一类问题）。

### 建议修法（待决策）

| 方案 | 代价 | 效果 |
|---|---|---|
| **A. 失败可见**（推荐先做） | 小 | 监听 `tileerror`；任务详情显示创建时间，超过阈值时提示"图层链接可能已过期，请重新运行" |
| B. 按需重建瓦片地址 | 中 | 打开历史任务时重新执行 `getMapId` 换取新令牌，需重跑 GEE 侧的一段代码 |
| C. 任务落地时缓存瓦片图 | 大 | 存储压力大，不适合本机演示环境 |

## 六、我自己的测量错误（如实记录）

这轮自检里，**被我误判为"产品缺陷"的三次，最后都证明是我的工具错**。记下来，因为它们比产品缺陷更容易骗人：

| 我的错误结论 | 真实原因 |
|---|---|
| "山西省 AOI 超出视口 3.15 倍" | Leaflet **残留瓦片**：上一屏的瓦片还在 DOM 里且 zoom 更高。**只有缩小方向会中招**（放大时旧瓦片 zoom 更低，取 `max` 仍正确）。修正方式：每测一项重载页面 + 只统计 `offsetParent !== null` 的瓦片 |
| "视野太宽，AOI 没撑满" | 方形 AOI 放进 965×380 的宽扁画布，`fitBounds` 必然左右留白。**只看宽度填充率必然误判**，要看受限的那一维 |
| "地图层级被算错了" | 用网络请求的众数选层级：Leaflet 在缩放动画期间会在中间层级也加载瓦片，且缓存命中不产生网络请求（实测 DOM 有 40 张瓦片而网络只有 8 个请求）。改用 **DOM** 作为真相来源，`神农溪` 的落点从 24.9 km 修正到 **8.1 km** |

**回验确认**：用修正后的工具重跑第一轮，**结论不变（5/5）**，只是距离从 3.7–18.8 km 收敛到 0–1.3 km —— 工具 bug 抬高了距离读数，没有颠倒结论。

## 八、坐标核定（已闭环）

上一轮补进库的 3 条区域，坐标是"按公开资料给出、尚未人工核定"的占位值。已逐条核定完毕。

**核定方法**（不依赖外部地理编码服务——本机 Nominatim/OSM 的地理编码接口不通）：
既然 OSM 的**瓦片**是通的（后端 `/api/basemap` 已代理），就反过来做——**把库里的坐标当输入**，渲染该点周边的真实地图，在**精确像素位置**打十字准星，再看地图上的真实地名是否吻合。瓦片来自 OSM、不是本项目自己的数据，构成独立证据。

方法本身先自证了两件事：

- **校准**：`广州市` 的准星落在广州市城区（西南佛山市、东东莞市、南番禺区）；`太湖` 落在湖面上 → 坐标系与投影没算错。
- **反面对照**：故意给一个错坐标 (91.10, 33.20)，渲染出来是唐古拉/羌塘一带的湖泊群（玛曲乡/岗尼乡/雁石坪镇），**没有出现「青海湖」** → 它不会"顺着"目标名显示。

| 区域 | 结论 |
|---|---|
| 泸沽湖 | ✅ 准星正落在**「泸沽湖镇」**，西邻永宁镇、东南盐源县、南邻宁蒗县 → 川滇交界，正确 |
| 民勤县 | ✅ 准星正落在**「民勤县」**县治，四周荒漠、东南为「民勤连古城国家级自然保护区」→ 正确 |
| 塔里木河 | ❌ **原值 (84.00, 40.40) 落在塔克拉玛干沙漠腹地** → 已修正 |

### 塔里木河的修正依据

沿 **84°E 做南北剖面**（z=10）实测：

- **河道在 ≈41.1°N** —— 蓝色水道 + 沿岸绿色植被带，地图上直接标着「塔里木河」
- 沿岸绿带南缘 ≈ **40.75°**
- 原值 **40.40 位于其南侧纯沙漠中，与河道相距约 0.8°（≈88 km）**

正向复核：候选点 (84.00, 41.20) 的准星落在河谷绿带上，紧邻「轮南镇」「塔里木镇」——正是塔里木河沿线地名。**已改为 (84.00, 41.15)。**

> 这个错值不会被任何接口断言或 bbox 判据发现：它仍在新疆、仍"看起来合理"，
> 只有把地图渲染出来看，才知道那是沙漠。**坐标本身写错，是回归盲区。**

对应的守卫已加入 `test_region_map_fallback.py`（117 → 120 项），把量出来的边界钉住（塔里木河 40.9~41.5°N，**下限 40.9 是有意的——原错误值 40.40 必须被拦住**）。
