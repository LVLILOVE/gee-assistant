**迁移在真实库上的实跑结果**

```
[数据归属] 已把 22 条历史任务划归管理员（user_id=1）
```

老数据没有变成"孤儿"：首个管理员注册时自动接管，无需手工 SQL。

> **为什么越权返 404 而不是 403**：403 等于承认"这个任务 ID 确实存在"，
> 会把别人的任务 ID 空间变成一个可逐位探测的信息泄漏面。404 让"不存在"与"不是你的"不可区分。

> **为什么要改 `regions` 的主键**：旧结构是 `name` 单列主键 + `INSERT OR REPLACE`，
> 于是「B 保存一个与 A 同名的区域」会**直接替换掉 A 那一行** —— 坐标变 B 的、
> `user_id` 也变成 B，A 的区域从自己列表里凭空消失且再也删不掉。
> 这是真实的跨用户数据破坏，所以必须改成联合主键 `(name, user_id)`。

### 3.15 验证过程中的一次"假绿"（记录下来备查）

首次跑探针 B 时，结果是这样：**能打开页面、能注册成功、但「历史任务」列表为空**，`PRE_JS` 直接返回
`{ok:false, why:'历史任务列表为空'}`。看起来像前端 bug。

实际原因与产品代码无关：起验证实例时 `APP_DB_PATH` 用的是 `$PWD/.browser_verify/app.db`。
Git Bash 的 `$PWD` 是 `/c/Users/...` 形式，这个字符串交给 **Windows 上的 Python** 去
`Path(...).resolve()`，会被当成**当前盘符根目录下的相对路径** → `C:\c\Users\...`。
`DB_DIR.mkdir(parents=True)` 会把这条不存在的目录链老老实实建出来，于是服务在
`C:\c\...` 下新建了一个**空库**，探针自然看到 0 条任务。

值得警惕的是：**同一类错误也存在于 `test_isolation_http.sh` 里**（临时库全部落在 `C:\c\`），
而那个脚本的 47 项断言**照样全绿** —— 因为服务端和断言用的是同一个错路径，自洽。
若不追查，就会以为"隔离验过了"，其实验的是一份空数据。

已做的三处修正（见 `backend/tools/test_isolation_http.sh`）：

### 3.16 任务配额与并发限制（`tools/test_quota_http.sh`，27 项）

补这层的起因：鉴权只挡住「没账号的人」，**挡不住「注册一个号然后无限提交」**。
服务在公网且允许自助注册，而每条任务都要烧 DeepSeek token 并占用 GEE 云端算力。
检查代码后确认当时提交口**没有任何配额或并发约束**。

测试用独立实例（`:8014` + 临时库 + `offline` 后端），把额度调到极小以便几秒内触发：

| # | 用例组 | 覆盖 |
|---|---|---|
| 1–2 | 全局 / 单用户并发 | 达上限返 `429`，`Retry-After` 存在 |
| 3–4 | 滑动窗口速率 | 每小时 / 每天上限，`Retry-After` 分别为 3600 / 86400 |
| 5 | 429 语义 | 响应体是带 `detail` 的 JSON，不是空响应 |
| 6 | 额度不串用户 | A 被限流不影响 B 的额度 |
| 7–8 | 额度跨重启 | 重启后已用额度**不清零**（计数来自库，不是内存） |
| 9 | 僵尸任务 | 重启后遗留 `running` 被标记 `failed`、日志含"服务重启"、**并发名额被释放** |
| 10 | 服务端无异常 | 日志无 Traceback |

**两个设计点值得单独说：**

1. **`_ensure_task_quota()` 的调用方必须持有 `_submit_lock`**。校验和 `store.create()`
   若不在同一临界区，两个并发提交会同时读到"还差一个名额"然后都放行 —— 配额形同虚设。
2. **僵尸任务不是"显示问题"而是"额度泄漏"**：重启后被遗留的 `pending`/`running`

结果：**27/27 通过**。

### 3.17 CORS 收窄（`tools/test_auth_http.sh` 第 11 组）

```bash

```

响应里出现了


**任意 Origin 都被原样回显**，等于告诉浏览器「任何网站都可以带着用户的 cookie 读这个接口」。

但这属于"靠另一层挡住所以没出事"——只要哪天为了支持独立前端把 Cookie 改成
`SameSite=None`，它立刻变成**「任意网站可读取你的全部任务列表」**。

关键判断：**生产环境前端由本服务同源托管，根本不需要 CORS**。
所以改成白名单，默认只放行 Vite 开发端口，可用 `CORS_ORIGINS` 追加。

| 断言 | 结果 |
|---|---|
| 陌生 Origin 不被回显 | ✅ 空 |
| 陌生 Origin 不变通为 `*` | ✅ 空 |
| `localhost:5173` 开发来源可用 | ✅ 回显该 Origin |
| 陌生 Origin 预检也不放行 | ✅ 空 |

### 3.18 一次"测试打了生产库"的事故（重要，改造了测试纪律）

**发生了什么**：脚本注册的固定用户名成了库里的**首个用户**，于是

   而服务就在公网上。

换句话说：**隔离功能本身工作正常，是测试把它推到了错误状态。**

**处置**（已全部完成）：

1. 备份 `data/app.db` → `.db_backup/app.db.before-testuser-cleanup`；
2. 按 `user_id` 逐表清理：`tasks` 归属**回退**为 `0`（不删数据）、`sessions` / `users` 删除；
3. 复核：`users=0`、`tasks` 22 条全部 `user_id=0`、`sessions=0`、无残留；
4. 线上实例重启后复核 `/health` 200、匿名 `/api/tasks` 401。

**根因与改造**：会写库的测试**绝不能指向生产**。做了两件事：

- `test_auth_http.sh` 改为**自起临时实例**（`:8015` + `APP_DB_PATH` 临时库 + `trap` 清理），
  和 `test_isolation_http.sh` / `test_quota_http.sh` 一致。顺带修掉它**不可重复运行**的问题
  （原先第二次跑时用户已存在 → 注册断言 409 → 带 cookie 的断言全部级联失败，看起来像产品坏了）。
- 新增 **`tools/smoke_live.sh`**：**严格只读**的线上冒烟（不注册、不登录、不写库），

  这才是该对生产跑的东西。

同时记下两条测试写法上的坑：

- **Cookie jar（Netscape 格式）不保留 `SameSite`**。它只保留 `HttpOnly`（写成 `#HttpOnly_` 前缀）
  与 `secure` 标记。所以检查 `SameSite` 必须读**原始响应头**（curl `-D`），读 jar 会假失败。

  误读成"鉴权失效"。`smoke_live.sh` 的 `code()` 因此带 4 次重试。

> 教训：**"会写库"和"能重复跑"是自动化测试的底线**。
> 一个会改生产数据、而且第二次就跑不通的脚本，比没有这个脚本更危险。

### 3.19 一个"匿名可读走后端配置与数据库"的路径穿越（本轮最严重）

**怎么撞上的**：收尾时想确认有没有 `/api/health` 这个探活端点（真正的探活是 `/health`），
顺手 curl 了一下，结果拿到 **200 + 前端 `index.html`**。一个不存在的接口返回 200，
说明 SPA 兜底路由 `@app.get("/{full_path:path}")` 把**所有没匹配上的 GET 都吞了**。
顺着这条线去看代码，就看到了洞：

```python
candidate = FRONTEND_DIST / full_path
if candidate.is_file():
    return FileResponse(candidate)      # ← 只判了 is_file()
```

**实测结果**（本地 `:8010`，`curl --path-as-is`，修复前）：

| 请求 | 修复前 | 拿到的是什么 |
|---|---|---|
| `GET /%2e%2e/%2e%2e/backend/app/config.py` | **200 · `text/x-python` · 5435 B** | 后端源码 |
| `GET /%2e%2e/%2e%2e/backend/.env` | **200 · `application/octet-stream` · 2717 B** | 含 `DEEPSEEK_API_KEY` 等凭据 |
| `GET /%2e%2e/%2e%2e/backend/data/app.db` | **200 · `application/octet-stream` · 233472 B** | 整库（用户 / 密码哈希 / 会话 / 任务） |
| `GET /api/nope-xyz` | 200 · `text/html` | 打错的接口拿到 200 而不是 404 |

**公网同样打得通**。修复后重新发同一批请求，服务端日志记到：

```
INFO:     14.19.47.224:0 - "GET /../../backend/.env HTTP/1.1" 404 Not Found
```

客户端 IP 是 cpolar 的出口，路径里的 `..` **原样穿过隧道**到达了应用 —— 也就是说
修复前这一批请求从公网发出来也是一样的结果。这条路由**没有任何鉴权依赖**。

**根因链**（四步缺一不可）：

1. `%2e` 是 `.` 的合法编码，uvicorn 在构造 ASGI scope 前就把它解码了；
2. `FRONTEND_DIST / "../../backend/.env"` 直接越出 `dist/` 目录，`Path` 不做任何限制；
3. `is_file()` 对越界路径照样返回 `True`；
4. 这条兜底路由没有鉴权，且它是"最后一条"，任何 GET 都会走到它。

**修复**（`backend/app/main.py`）：

1. 新增 `_safe_dist_file()`：`resolve()` 之后必须 `is_relative_to(FRONTEND_DIST)`，
   否则返回 `None`。`resolve()` 会一并解开符号链接，所以"在 dist 里放个软链指向外面"也挡住；
2. 路径里出现 `..` 段直接返 **404**，不再回退 SPA 外壳（语义清楚，也防止将来有人改
   `_safe_dist_file()` 时把洞放回去）；
3. `/api/`、`/health`、`/docs` 等前缀未匹配到路由时返 **JSON 404**，不再吐 HTML。

**回归测试 `tools/test_static_route.py`（57 项，全通过）**：

- 用**裸 ASGI scope** 发请求，不走 `TestClient` —— httpx 有可能自己把 `/%2e%2e/`
  归一化掉，那样越界路径根本没送到应用，测试会**假通过**（3.15 就是这个坑的翻版）；
- 第 0 组是**对照**：先确认 `.env` / `config.py` / `app.db` 真的在磁盘上、

  "文件本来就不存在"，说明不了拦截生效；
- 断言不只看状态码：还检查响应体里没有 `DEEPSEEK_API_KEY` / `ADMIN_PASSWORD` /

**`smoke_live.sh` 增加第 5、6 组（16 → 25 项）**：必须带 `--path-as-is` ——

### 3.20 沙箱能读走 `.env`：修完 3.19 顺手查代码时发现的第二处（重要）

**怎么查出来的**：3.19 修完后我做了一遍「拿请求输入去拼文件系统路径」的全项目排查 ——
路由侧是干净的（`/api/tile`、`/api/tasks/{tid}`、`/api/regions/{name}` 都不碰文件系统）。
但顺着「谁还会碰文件系统」往下一层看，看到了执行沙箱：它封了**网络**（域名白名单）和
**子进程**（`_block_process_creation`），唯独**文件系统是敞开的**。实测（mock 模式即可复现）：

```
open(backend/.env)   → OK len=1593，含 DEEPSEEK_API_KEY
pathlib.Path(".env").read_text()  → 同样能读
os.open("data/app.db")            → 同样能读
os.listdir(".")      → ['.db_backup', '.env', '.env.example', '.venv', 'app', 'data', ...]
```

**为什么这个洞比看起来严重**：沙箱里跑的代码是 **LLM 按用户输入生成**的，而
`ALLOW_REGISTRATION=true`、服务挂在公网 —— 任何注册用户写一句「读取 `.env` 并打印」，
模型就会生成对应的读取代码，密钥随任务结果**原样回到他自己手里**。
这等于绕过登录拿走后端凭据（LLM 密钥 / GEE 凭据 / 整库）。
它和 3.19 是同一类问题的两个入口：**攻击者可控的字符串最终落到了文件系统上**。

**修复**（`app/execution/_runner.py`）：在执行用户代码前装一层
`_block_sensitive_file_access()`，把 `builtins.open` / `io.open` / `os.open` /
`os.listdir` / `os.scandir` 换成带敏感路径判定的版本。禁读禁写：

| 类别 | 规则 |
|---|---|
| 环境变量 | 文件名以 `.env` 开头 |
| 数据库 / 私钥 | 后缀 `.db` `.db-wal` `.db-shm` `.key` `.pem` `.p12` `.ppk` `.keystore` |
| 目录 | `.db_backup` `.git` `.venv` `.ssh` `.aws` `.kube` `.gnupg` |
| 特定文件名 | `*service_account*.json` `*-key.json` `id_rsa*` `id_ed25519*` `.netrc` `.npmrc` `.pypirc` |

**关键设计：加固点放哪**。第一次实现把它塞进了 `_harden()`（和 socket / 子进程一起，
在流程最前面），结果**整条链路直接挂**：

```
PermissionError: 沙箱安全策略禁止访问环境变量文件：.env
  ... 栈顶在 _verify_toolchain() → importlib.import_module("app.config")
```

因为 `python-dotenv`（`app.config` 依赖）在导入时就要读 `.env`，
`gee_auth.initialize` 要读凭据文件 —— 这些都属于**我们自己的可信代码**。
正确位置是 **`_verify_toolchain()` / `_install_ee()` 之后、`exec(用户代码)` 之前**：
加固只需要赶在模型生成的代码之前生效。

同时必须**显式放行凭据路径**（`data/credentials/`、`~/.config/earthengine`，
以及 `GEE_SERVICE_ACCOUNT_JSON` 等环境变量指向的确切文件），否则真实 GEE 初始化会失败 ——
`GEE_SERVICE_ACCOUNT_JSON` 可以指向任意位置任意文件名（例如 `D:\keys\my.json`），
只靠目录片段放行不够，所以把它 `realpath()` 后加进精确白名单。

**验证 `tools/test_sandbox_fs.py`（35 项，全通过）**：

- **三入口都验**：`open()` / `pathlib.Path.read_*()` / `os.open()` 三条完全不同的系统调用入口，
  只堵 `builtins.open` 会漏掉 `WriteFile` 那条；
- **反向断言**：普通源码文件（`sandbox.py`、`requirements.txt`）**必须仍可读** ——
  证明不是「把 open 一刀切禁掉」这种会打死工具链的粗暴做法；
- 目录列举 `.db_backup` / `.venv` 也必须被拒；
- **对照组**同 3.19：先确认 `.env` / `app.db` / 备份文件真在磁盘上；
- 每项探针都只针对**磁盘上确实存在**的文件，否则失败原因会混入 `FileNotFoundError`，
  区分不出「被拦住了」和「本来就没有」；
- 第 3 组是**对抗性绕过用例**（见下），第 4 组断言标准任务模板仍能跑通并正常上报图层/图表。

#### 3.20.1 第一版封禁是**不完整的** —— 对抗性测试把它挖了出来

这一点值得单独记，因为它是「测试全绿但功能没做到」的又一例，而且**只有主动去想
"还有什么别的方式做同一件事"才会暴露**。第一版只封了 `builtins.open` / `io.open` / `os.open`，
当时 26 项断言全通过。随后我写了一个绕过探针，逐个试 CPython 里同一能力的其他入口：

| 绕过入口 | 第一版结果 | 说明 |
|---|---|---|
| `io.FileIO(".env", "r")` | **BYPASSED** | 直接构造底层类，把上面两层包装全绕过去 |
| `io.open_code(".env")` | **BYPASSED** | 又一条独立入口 |
| `os.stat(".env")` | **BYPASSED** | 只泄露大小（2717），但足以做存在性 / 变化探测 |
| `io.FileIO("data/app.db", "r")` | **BYPASSED** | 读出了 `SQLite format 3` —— 整库 |
| `codecs.open` / `pathlib.Path.open` / `json.load(open(...))` | 已拦 | 走 `builtins.open`，被第一版覆盖 |
| `shutil.copyfile` | 已拦 | 同上 |

也就是说**第一版实际上拦不住真正的攻击者**：一句 `io.FileIO(".env").read()` 就回来了。
补上 `io.FileIO`（必须用**子类**替换，否则别处 `isinstance(f, io.FileIO)` 的判断会开始报错）、
`io.open_code`、`os.stat` / `os.lstat` 之后，8 个绕过入口全部 `BLOCKED`，
并额外断言**沙箱内确实没写出文件**（`leak.tmp` 不存在）——
只看状态码是不够的，"先写出去了才报错"同样会显示 `BLOCKED`。

> 教训：**「封禁某种能力」要把这个能力的全部入口列出来再逐个封，不能只堵最常见的那一个。**
> 这和 `_block_process_creation` 里"只封 `subprocess.Popen` 会漏掉 `_winapi.CreateProcess`"
> 是同一个道理 —— 那条注释本来就写在代码里，却没有照着做，所以又踩了一次。

## 5. 已知问题与限制

1. **服务账号凭据未导入**：当前真实 GEE 执行走的是**个人 OAuth 路线**（已验证可用，见 3.11 的地图瓦片实测）。
   服务账号路线的代码与存储链路已 `tools/test_sa_route.py` 44 项验通，只差在 Google Cloud Console
   建服务账号并授予 `Earth Engine Resource Viewer` + `Service Usage Consumer` 两项角色；
   导入命令 `tools/gee_doctor.py --import-sa "C:\路径\key.json"`。
   ⚠ 注意服务账号优先级**高于**个人 OAuth，导入后若不可用用 `--drop-sa` 回退。
2. **意图识别准确率指标未正式评估**：当前为 DeepSeek 解析 + 规则兜底双路，正式指标需标注测试集。
3. **cpolar 免费版域名随机**：重启后子域名变化，固定域名需升级。
   且隧道会**自己死掉**：2026-09-17 实测一次 cpolar 侧 DNS 抖动（`lookup cpolard.r31.cpolar.top: no such host`，
   同期 `nslookup` 能解析但首次超时 2 秒），cpolar 报错后**只维持控制连接心跳、不再重试隧道**，
   进程看着活着而公网已 404。处置办法是重启 cpolar，代价是子域名会变（`19f0a78b` → `792ed623`），
   对外发过的链接要重发。详见 `docs/部署手册.md` 5.3。
4. ~~**前端 chunk 体积较大**（约 2.0MB）~~ → **已优化**：按 `manualChunks` 拆 vendor +
   `React.lazy` 延迟加载地图/图表，首屏 JS 由 2,047,209 B 降至 **852,805 B（-58%）**，
   echarts/leaflet 不再进首屏；运行时按需加载已由真实浏览器验证（见 3.9 / 3.14）。
5. **管理员无额外数据权限**：管理员只看得到自己的任务（老数据已划归名下）。
   当前没有用户管理界面，如需"管理员审计全部任务"需另开口子。
6. **无密码找回 / 邮箱验证**：注册不需要邮箱，忘记密码只能由管理员在库里重置。
7. **测试脚本的执行纪律**：会写库的脚本必须自带临时实例与 `APP_DB_PATH`，
   对生产只允许跑只读的 `smoke_live.sh`。这条曾以一次真实事故为代价确立（见 3.18）——
   `test_auth_http.sh` 打过线上库，注册出的测试账号成了首个管理员并接管了 22 条历史任务。
8. **`DEEPSEEK_API_KEY` 建议吊销重发**（见 3.19 / 3.20）：修复前 `backend/.env` 有**两条**匿名可读路径 ——
   静态托管的路径穿越，以及沙箱里生成代码的 `open()`。密钥应按已泄漏处理。
   数据库同样可读，但当时 `users=0`/`sessions=0`，无真实账号凭据外泄。
   **这是需要用户到 DeepSeek 控制台操作的外部动作。**
9. **沙箱的文件隔离是"敏感项名单"而不是"全封闭"**（见 3.20）：当前策略是
   「精确放行 GEE 凭据 + 其余敏感项禁读」，普通源码文件仍可读。
   更彻底的做法是**不让沙箱碰文件系统** —— 由父进程解密凭据后经 stdin 的
   `request` payload 传进去，沙箱只许读一个临时工作目录。
   这需要改动 `gee_auth.initialize()` 的取值方式，属于对核心执行链的改动，本次未做。

## 6. 结论

系统核心链路（意图解析 → 代码生成 → 沙箱执行 → 自动调试 → 可视化）已全链路跑通并通过测试：四类任务、多轮澄清、持久化、报告导出、常用区域、对外发布均验证通过，且已在真实 Earth Engine 上跑出结果（无头浏览器实测瓦片全 200、0 报错）。

安全与多用户方面：注册登录、访问控制、失败节流、密码哈希、GEE 凭据加密存储与可逆回退、三张业务表按用户隔离、旧库自动迁移、任务配额与并发限制、CORS 来源白名单、静态托管的路径穿越防护、沙箱的文件系统隔离，均有自动化脚本覆盖，累计 **385 项断言（383 通过 / 2 明确跳过 / 0 失败）**，另有 **25 项只读线上冒烟**在本地与公网地址上均通过。

**四个量化指标**（任务书 2.2 第 6 条）已由固定评测集实测，全部达标：意图识别 39/39（3 轮 × 13 条）、一次执行成功率 8/8、调试后完成率 8/8、典型任务耗时中位数 56.5s。
两点口径必须一并说明：① 耗时按**中位数**口径达标，其中 **3 条单次超过 60s**（最长 76s），若验收口径是"每条都 ≤60s"则该指标不达标；② 8 条端到端样本量小，其价值是**覆盖**四类任务 × 2 个区域/时段，而非给出高置信度成功率。
详见 `docs/评测报告-2026-09-17.md` 与 `docs/产品评估报告.md` 9.3 节。

另有一类**不随测试变绿而消失**的风险已单独加守卫：全栈曾散落 8 处写死的默认日期
（跨后端 4 模块 + 前端 2 处），全部过期一年以上，其中最难查的是"模型对模糊时间返回 null 时
被兜底值静默钉死在 2024 年"。现已收口到 `app/daterange.py` 单一来源，并用
`tools/test_no_stale_year.py` 22 项断言锁定 —— 该守卫断言的不是"当前值对不对"，
而是**"值是否随当天推算"**，因此它今天能过、明年也能过，但一旦有人再写死日期就立刻失败。

需要说明的是，本轮有五处结论是**靠追查改出来的**，而不是靠测试变绿确认的：

1. 前端验证的"假绿"（3.15）—— 测试台指向了错误路径，而服务端与断言用同一个错路径，自洽全绿；
2. 测试脚本写坏生产数据（3.18）—— 脚本会注册账号却打的是线上库，注册出的固定用户名成了首个管理员并接管了 22 条历史任务；
3. CORS 宽配置（3.17）—— 实测任意 Origin 都被回显，当时靠 `SameSite=Lax` 兜住，属于"靠另一层挡住所以没出事"；
4. **路径穿越（3.19）** —— 起因是想确认一个探活端点是否存在，却发现不存在的接口返回 200 + HTML。
   顺着"为什么会返 200"看下去，才挖出匿名可读 `.env` 与数据库的洞；
5. **沙箱读 `.env`（3.20）** —— 修完第 4 条后做"攻击者可控字符串最终落到哪里"的排查，
   发现同一个问题在另一层入口又出现了一次：沙箱只封了网络与子进程，文件系统是敞开的。

> 这五条的共性：**测试全绿不等于没问题，只等于"测试写过的地方"没问题。**
> 真正找出问题的是"对一个意外现象追到底"——一个不该出现的 200、一个回显的 Origin、
> 一个第二个用户就成了管理员的库。收尾时顺手多 probe 一下不存在的路径，比再补十个 happy-path 用例更有用。
>
> 第 4、5 条还给出一个可复用的排查手法：**顺着"外部输入最终流到了哪个危险操作"去走一遍**
> （请求参数 → 文件路径 / SQL / 子进程 / 网络），比逐个端点看实现更容易发现漏网的那一层。
> 两条都是"同一个根因、两个入口"，只修看到的那个入口是不够的。

三次都表现为**测试全绿而实际什么都没验到、甚至验成了反的**，或**靠别的机制掩盖了缺陷**。因此把纪律写进了问题清单：会写库的测试自带临时实例，生产只跑只读脚本；安全相关配置要**实测响应头**而不是读代码。

前端方面：代码分割与懒加载经无头浏览器实测确认生效（首屏无 echarts/leaflet、交互后才加载、全程 0 报错），首屏 JS 体积下降 58%。

后续需补充的是量化指标（一次成功率、调试后完成率）的正式评估，以及按任务书要求开展的用户验收测试。
