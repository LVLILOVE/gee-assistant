## 三、量化指标：任务书硬要求，目前是最大缺口

任务书 2.2 第 6 条明确了四大量化指标。这是**验收的硬杠**，也是目前唯一"完全没有证据"的部分。

| 指标 | 任务书要求 | 当前证据 | 状态 |
|---|---|---|---|
| 意图识别准确率 | ≥90% | 无标注测试集，从未评估 | ❌ 无数据 |
| 代码一次执行成功率 | ≥70% | 无正式评测；**但库里 22 条历史任务可算出 19/22 = 86.4%** | 🔶 有信号，无证据 |
| 调试后完成率 | ≥85% | 无正式评测；**库里可算出 21/22 = 95.5%** | 🔶 有信号，无证据 |
| 典型任务端到端耗时 | ≤60 秒 | **数据库无耗时字段，架构上就测不出来** | ❌ 无法测量 |

### 这里有个好消息和一个坏消息

**好消息**：从线上库的 22 条真实任务记录看，**两个成功率指标很可能已经达标**（86.4% / 95.5%），
尝试次数分布为「1 次成功 19 条、2 次 2 条、3 次 1 条」——自动调试确实在起作用。

**坏消息**：这些是开发者自测样本，**不能作为验收证据**，原因有三：

1. 样本量太小（22 条），且任务类型不均衡（NDVI 占绝大多数）；
2. 不是**受控评测**：没有固定的任务清单与判据，别人无法复现；
3. **耗时指标在数据模型上就缺失** —— `tasks` 表只有 `created_at`，没有 `finished_at` / `duration`，
   想测也测不出来。这条必须先加字段。

> **建议动作**：把"建评测集"拆成最小可交付版本 —— 不必搞 100 条。
> 30 条意图解析标注 + 20 条端到端任务脚本 + 一个 `tools/eval_metrics.py`，
> 就能把三个指标从"无数据"变成"有证据"。工作量约半天，是当前**投入产出比最高的一件事**。

## 四、被忽略的合规要求：两条任务书白纸黑字，但没做

这两条容易被"功能都跑通了"的兴奋盖过去，但它们是任务书原文要求，属于**会被评审直接问到**的点。

### 4.1 移动端适配 —— 任务书 3.1 明确要求，实际 0 实现

任务书 3.1：「前端（Web 客户端）……**采用响应式设计适配 PC 端和移动端浏览器**」。
`docs/UI-UX设计.md` 第 7 节也规划了「移动端：单列堆叠，对话优先（🔶 第二周打磨）」。

**实际情况**：`frontend/src/style.css` 里 `@media` 查询数量为 **0**。也就是说设计写了、代码没做。

这不只是"少了个功能"，而是**和真实使用场景错配**：
环保监测、农业巡查的一线人员，最需要看结果的时刻恰恰是在**户外、手机上**。
PC 优先是开发便利，不是用户需要。

### 4.2 数据库存储加密 —— 任务书 6.2 明确要求，业务数据仍是明文

任务书 6.2：「用户的分析区域、任务描述与平台账号凭据可能涉及敏感信息，应采取
HTTPS 加密传输、**数据库存储加密**等措施」。

现状是**一半做到、一半没做**：

| 数据 | 状态 |
|---|---|
| GEE 凭据 | ✅ Fernet 对称加密落盘，密钥单独存 `.key`（`app/secure_store.py`） |
| 用户密码 | ✅ PBKDF2-HMAC-SHA256 加盐哈希（本就不该可逆） |
| **任务描述 / 区域名 / 生成的代码 / 结果** | ❌ **明文存在 sqlite** |

`task_store.py` 里没有任何加密逻辑。用户输入的"我要分析某敏感区域的污染情况"这类描述，
是明文躺在 `data/app.db` 里的。

> **判断**：这一条的严重度不高（本地部署、单机库），但**属于任务书明确写了却没做的项**。
> 处理方式可以轻量：在文档里明确说明"当前为本地化部署，库文件受操作系统权限保护，
> 生产化部署时应启用 SQLCipher 或字段级加密"，比什么都不说更稳妥。

## 六、改进意见（超出任务书的部分）

任务书写的是"做成什么"，下面这几条是"能不能真被用起来"。按重要性排序。

### 6.1 最大风险不是技术，而是「没有用户」

这是我最想强调的一点。项目在技术上的完成度**远超**一个课程/答辩项目该有的水平 ——
385 项自动化断言、三次安全漏洞的真实修复、`404 而非 403` 这类细粒度考量，
很多上线产品都做不到。**但至今没有任何真实用户用过它。**

这意味着以下判断全部是"未经验证的假设"：

- 「零代码用户用一句中文就能完成分析」—— 真的吗？他们的表达方式是什么样？
- 「自动调试对用户是透明的」—— 用户看到"第 1 次失败"，是更信任还是更怀疑？
- 「地图 + 折线图就是他们要的结果」—— 环保工程师要的是"结论摘要"还是"原始图表"？
- 「示例 prompt 够用」—— 3 条硬编码示例（`App.jsx:731`）能覆盖多复杂的真实需求？

> **建议**：答辩前无论如何找 **2–3 位目标用户**（哪怕是同学扮演）各跑 3 个需求，
> 记录卡在哪一步、问了什么问题。这份 UAT 记录的价值**高于再加十个功能** ——
> 因为它是唯一能让"产品"这两个字站住脚的东西。

### 6.2 补上"从图到结论"的最后一跳

当前输出是**图层 + 统计图表 + 可查看的代码**。对非专业用户来说，图看完了还是不知道
"所以我该做什么"。这是"零代码"产品最容易在最后一公里失败的地方。

建议在结果区加一个**结论摘要卡片**，把统计量翻译成业务语言，例如：

> 太湖流域 2026 年 1–12 月 NDVI 均值 0.52，7–8 月达峰值 0.61，**植被覆盖良好**；
> 相比去年同期上升 3.2%，主要增幅出现在湖区东部。

这件事**几乎不需要新算力** —— 数据已经在手，只是差一次 LLM 的"结果解释"调用。
投入产出比极高。（顺带能自然带出任务书 6.1 要求的 AI 生成标识。）

### 6.3 让用户"敢用" AI 生成的结论

AI 生成的遥感结论，专业用户的天然反应是"我凭什么信"。当前产品有三个可加强的信任支点：

- **可解释**：已有"查看生成的 GEE 代码"（做得很好，建议默认展开、而非折叠）；
- **可追溯**：展示本次分析实际用了哪个数据集、时间范围、云量阈值（部分已有）；
- **有分寸**：明确标出不确定性与适用边界（如"云遮挡可能影响结论"），
  这既是任务书 6.3 的要求，也是专业用户最认可的态度。

### 6.4 成本与可持续性

- cpolar 免费版**不适合作为生产方案**：域名随机、隧道会死。真要对外提供服务，
  需要固定域名 + 一台常驻机器；
- 每次任务烧 DeepSeek token + GEE 云端配额。当前四层配额是"防滥用"，下一步应做成
  **"可计量 + 可预算"**，否则无法回答"这个服务一个月要多少钱"。

## 八、总结

这个项目的状态可以概括为：

> **技术实现是"超标"的，验收证据是"欠账"的，产品验证是"空白"的。**

- **超标的部分**应该被讲出来（PPT 目前反而讲少了）：真实 GEE 接入、多用户隔离、
  四层配额、三处安全漏洞的真实修复与 385 项自动化断言；
- **欠账的部分**是任务书明确要求但缺证据的：四个量化指标、移动端适配、数据加密；
- **空白的部分**是产品的灵魂：**没有一个真实用户用过**。

前两类是"收尾工作"，工作量可控，按第七节的顺序做完即可。
第三类才是决定这个项目是"一个跑通的技术 demo"还是"一个能用的产品"的分水岭。

#### 9.3.1 结果：四个指标两轮都达标，但口径必须说清

同一固定评测集、同一天内**独立跑了两轮**。结果**并不相同**：

| 指标 | 目标 | 第 1 轮 | 第 2 轮 | 判定 |
|---|---|---|---|---|
| 意图识别准确率 | ≥ 90% | 39/39 = **100%** | 39/39 = **100%** | 达标（3 轮 × 13 条，稳定） |
| 一次执行成功率 | ≥ 70% | 8/8 = **100%** | **7/8 = 87.5%** | 达标 |
| 调试后完成率 | ≥ 85% | 8/8 = **100%** | **7/8 = 87.5%** | 达标（**压线**） |
| 典型任务耗时 | ≤ 60s | 中位数 **47.5s** | 中位数 **53.2s** | 达标（口径见下） |
| └ 单条 >60s 的条数 | — | 3/8（最长 76.0s） | 2/8（最长 82.3s） | 口径相关 |

**⚠️ 口径零（最重要）：这些是样本，不是稳定值。**
第 2 轮里 `e2e-classification-长三角` 3 次重试全部失败，而第 1 轮同一用例是成功的。
所以**单轮的 8/8 不能当作结论**——它是一次抽样。汇报与答辩一律按**区间**报
（一次成功率 87.5%~100%、耗时中位数 47.5~53.2s），并说明样本量。
只引用最好那一轮，等于自欺。

**⚠️ 口径一：耗时是"中位数达标"，不是"每条都达标"。**
两轮分别有 3 条和 2 条单次超过 60s（最长 82.3s）。本项按**中位数**判定"典型任务耗时"；
若验收口径是"所有任务都 ≤60s"，则该指标**不达标**。报告已把超标条目逐条列出，
这个判断应由验收方看过数字后作出，不由报告代为决定。
耗时口径 = `finished_at - started_at`（真实执行），**不含排队**（`created_at→started_at`，实测约 0.1s）。

**⚠️ 口径二：8 条样本是"覆盖"而非"统计"。**
样本量小，一次失败就摆动 12.5%。它的价值在于覆盖四类任务 × 2 个区域/时段
（即"同类任务换个区域也能跑通"），而不是给出高置信度的成功率。

**⚠️ 口径三：调试后完成率 87.5% 距目标线 85% 只差 2.5 个百分点**——再多一条失败就掉到 75%
（不达标）。这一项**没有余量**，答辩时不要把它说成"稳过"。

**⚠️ 口径四：意图识别是压线指标。**
同一批 13 条用例，更早曾跑出 100% 与 **84.6%**（目标线 90%）。所以 runner 默认重复 3 轮、
报平均值 + 单轮区间 + 逐用例稳定性。**修完 region 抽取缺陷后连续多轮稳定 100%**（详见 9.3.2 第 ③ 条）。
只报单轮 100% 会误导，必须给区间。

#### 9.3.2 评测过程发现并修掉的六类问题

**① 变化检测任务连续 3 次失败，自动调试全部无效（真实产品缺陷）**

现象：变化检测任务报 `KeyError: 'ndvi'`，**自动调试 3 次全部原样失败**。

根因分两层：

- **生成代码的 bug**：`ndvi_series = [f['properties']['ndvi'] for f in ...]` 硬取属性键。
  Earth Engine 里 Feature 属性值为 `None` 时，`getInfo()` 返回的 properties 中
  **根本不会有这个键**——而 codegen 早已要求"空月返回 None"（规则 g），
  两条规则撞在一起就必然炸。**源头是对的，下游消费方式错了。**
- **调试器的盲区**：`debugger.summarize_error()` 只返回 `error["message"]`，
  把 `error["traceback"]` **整个丢弃**。而沙箱早已把 traceback 采集好，里面明确写着
  `File "<gee_code>", line 72`。于是大模型只拿到 `KeyError: 'ndvi'`，
  却要在 5300 字符的代码里猜位置——同一段代码里有两处 `ndvi`，猜错一次就白烧一轮重试。

修法：`debugger.py` 新增 `locate_error_line()` 从 traceback 抠出行号，
`summarize_error(error, code)` 把**行号 + 该行源码 + traceback 尾部**一起给大模型；
`codegen.py` 新增资源规则 `j`（None 属性会被省略，必须用 `.get()`）。

**效果**：该用例从"3 次重试全败"变为**第一次执行即成功**（`attempts=1`）。
**第 2 轮独立评测复现了这个结果**（`e2e-change-鄱阳湖` 再次 `attempts=1`、执行 56.0s），
所以这条修复有跨轮次证据，不是单次侥幸。

> **通用教训**：调试器拿不到位置信息时，"自动调试"就退化成"让大模型重写一遍碰运气"。
> 信息本来就在手里，没有理由丢。

**② 全栈 8 处「冻结年份」（收口为单一来源）**

建评测集前探测意图解析，发现"6-8 月"被补成 2025 年（提示词写死）。顺全局扫一遍，
**一共 8 处**，跨后端 4 个模块 + 前端 2 个位置：

| 位置 | 内容 | 症状 |
|---|---|---|
| `app/intent.py` 兜底 | `or "2024-01-01"` | **最隐蔽**：模型对"现在"返回 `null` 是**正确**行为，却被静默钉死在 2024 |
| `app/intent.py` / `app/planner.py` 提示词 | "补全为 2025 年" | 年份写死 |
| `app/codegen.py` 生成代码 | `or '2024-01-01'` | 过期基准会固化进交付给用户的脚本 |
| `app/models.py` 契约默认 | `= "2024-01-01"` | API 契约层 |
| `frontend/src/App.jsx` ×2 | 表单初始态 + 提交兜底 | 用户不改时间就拿两年前的数据 |
| `app/execution/offline.py` | 图表标签写死 `2020-2021…2023-2024` | 离线演示路径，让产品显得停在过去 |

修法：新建 `backend/app/daterange.py` 作为**唯一来源**。默认区间口径取
**「最近一个完整自然年」**（不是滚动 12 个月），理由是季节完整性、**年内可复现**
（滚动窗口每月漂移，默认结果没法做回归比对）、与原语义连续。
`models.py` 改用 `default_factory`——常量默认值在模块导入时只求值一次，服务长期不重启会跨年沿用旧值。

**加了一道回归守卫** `backend/tools/test_no_stale_year.py`（22 项）。它的断言刻意不是
"当前值对不对"，而是**"值是否随当天推算"**——今天能过、明年也能过，但一旦有人再写死日期就立刻失败。
因为这类 bug 有两个特点：不报错、且**修好之后还会再犯**（写死日期的那一刻它看起来永远是对的）。
守卫本身也验证过有效性：故意放一个含 `"2024-01-01"` 的文件 → 测试立刻 FAIL 并精确报出行号。

**③ 意图识别的 region 抽取不稳定（压线指标的成因）**

失败原因很具体、不偶发：「看看鄱阳湖现在的水域范围」被解析成
region = **"看看鄱阳湖"**（动词混进地名）；「太湖的水面面积最近有啥变化」region 直接丢空。
修法：提示词补充"region 只填地名本身，先剥掉动词与时间词"。修后 3 轮 × 13 条全部稳定通过。

**④ 评测工具自身的缺陷（会被误读成产品问题）**

第一遍评测跑完立刻跑第二遍，后 5 条全返回 429。原因是**产品自己的配额在正常工作**
（`TASK_RATE_LIMIT_PER_HOUR=20`，一小时内刚好提交满 20 条就拒下一条）——
但 runner 当时把 429 计入"任务失败"，指标二/三从 100% 掉到 25%。**测出来的其实是
"我提交得太快"，不是"产品不行"。**

修法：识别 429 → 读 `Retry-After` → 等待重试；配额拒绝/等待超时的用例**排除出指标分母**
并在报告里披露（不静默丢弃）。同类处理还有：`intent.parse` 在 DeepSeek 调用失败时会
**静默降级到规则兜底**，若不识别，一次 API 抖动就会被记成"识别错误"。

> **通则**：测量工具必须把「被测系统的失败」和「测量基础设施的问题」分开。
> 否则指标会随测量条件漂移，失去作为验收证据的资格。

**⑤ 顺带发现：`test_isolation.py` 曾静默失败（回归套件的问题，非产品问题）**

跑全量回归时发现该测试 **74/79**，5 项失败。排查确认**与本次改动无关**，而是
上一轮"预置管理员 + 划归 22 条历史任务"的连带后果：该测试第 2 节直接断言
"库里还没有用户 + 有 N 条无主任务"——**测试与生产数据状态耦合**，
生产状态一变（这恰恰是好事）测试就红，而且没人发现。

修法：第 2 节改为**自造前置条件**（复制库 → 清空用户 → 打回无主 → 再造用户验证接管），
期望值从库里现算而不写死条数。修后 79/79。

> **注意**：PPT 里"360 项断言全部通过"这句话，在该测试静默失败的那段时间内**并不成立**。
> 现已修正为 385 项（含 22 项年代漂移守卫 + 1 项分页契约断言）并在本轮全部跑通。

**⑥ 分类任务 3 次重试全败，自动调试又一次"原地打转"（第 2 轮抓到的真实缺陷）**

这是**与第 ① 条同一类**的缺陷，只是在另一个任务类型上复发——说明这类问题不是一次修完的。

现象：`e2e-classification-长三角`（任务 `140f1a9f66c4`）**3 次错误信息逐字相同**：

```
AttributeError: 'Image' object has no attribute 'mode'   （× 3 次）
```

逐字相同说明这次修复**没有产生任何改动**，三次跑的是等价代码。根因两层：

- **生成侧的 GEE API 幻觉**：`ee.Image` 根本没有 `.mode()`（它是 ImageCollection 的方法）。
  模型写了 `img.select('label').mode()` 求众数类别。
- **调试侧的位置误导**：traceback 把 `<gee_code>` 帧定在第 133 行
  `ee.List(months).map(monthly_class_stats)` —— 而**这一行本身完全正确**。
  真正的缺陷在被 `.map()` 的那个函数体里（回调里抛的异常，行号会指向调用点）。
  只给"第 133 行"，等于把模型引去改一行没问题的代码。

修法（三处）：

| 位置 | 改动 |
|---|---|
| `app/codegen.py` 资源规则 `k` | 写清 Image 与 ImageCollection 方法不通用、`.mode()` 的两条合法写法（`ImageCollection.mode()` / `Image.reduce(ee.Reducer.mode())`）、以及"`.select()/.clip()` 之后仍是 Image" |
| `app/debugger.py` 新增 `callback_note()` | 识别"出错行是 `.map()`/`.iterate()` 调用"，明说位置是调用点而非缺陷点，并把**被 map 的函数体完整抠出来**塞进修复提示 |
| `app/orchestrator.py` `_node_repair()` | 检测"修复后代码与上一次完全相同"，记日志并给下一轮附加强提醒——把静默白烧的一轮变成**可见事件** |

**效果**：同用例重新提交 → **首次执行即成功**（`attempts=1`，执行 105.7s）。

> ⚠ **但这条不能说过头**：复验只跑了 **1 次**。LLM 生成本身有随机性——该用例第 1 轮成功、
> 第 2 轮失败、修后 1 次成功。正确说法是"规则 k 关掉了这类错误的一个已知来源"，
> **不能**说"这个用例已稳定通过"。要下稳定结论只能多跑几轮。

> **两条可以带走的通则**：
> ①**「修了没修好」和「修复根本没发生」是两件事**。三次错误逐字相同，是后者的特征。
> 测量/调试链路里，凡是"自动重试"的地方都该判断"这次和上次有没有区别"。
> ②**回调式调用（`.map()`/`.iterate()`）里报错，行号指向调用点**。给出位置时必须带上这条限定，
> 否则"更精确的位置信息"反而会把模型带偏——这和第 ① 条是同一个教训的另一面。

#### 9.3.3 运营提示：评测不能连着跑两遍

一小时限额 20 条，一轮完整评测消耗 8 条，叠加前期调用很容易撞满，之后全部 429。

> 比一个漂亮的孤立数字经得起追问。

## 十一、安全复评（2026-09-20 下午 · 对抗性渗透测试）

### 11.1 为什么要做这次测试

起因是一次追问：「这个只是前端展示，后端的部分呢？」

在整理后端证据时，我意识到一个此前被跳过的问题：**沙箱一直在跑，但从没被攻击过。**
此前的全部测试（`test_sandbox_fs.py` 8 项对抗用例、`gee_doctor` 沙箱自检）
测的都是「**已知的**敏感文件读不到」，而不是「**任意**非预期操作能不能做到」。

这两件事差别很大：

> 常规测试测的是「预期路径能不能工作」；
> 渗透测试测的是「非预期路径能不能被挡住」。

于是补做了一轮对抗性渗透测试 —— 结果**破防**。

### 11.2 测试结果：9 项攻击面，穿透 4 项

| # | 攻击面 | 结果 | 危害 |
|---|---|---|---|
| 1 | 读 `backend/.env` | ❌ 拦截 | — |
| 2 | 读 `data/app.db` | ❌ 拦截 | — |
| 3 | **读 `C:/Windows/win.ini`** | ✅ **穿透** | 泄露系统文件 |
| 4 | **`os.listdir('C:/')`** | ✅ **穿透** | 泄露整盘目录结构 |
| 5 | **`os.stat('C:/Windows')`** | ✅ **穿透** | 存在性与变化探测 |
| 6 | 起子进程 | ❌ 拦截 | — |
| 7 | 导入 `ctypes` | ❌ 拦截 | — |
| 8 | 连非白名单域名 | ❌ 拦截 | — |
| 9 | **写 `<工程目录>/hacked.txt`** | ✅ **穿透** | **服务端任意写文件（高危）** |

### 11.3 第 9 项是高危漏洞，必须单独说清

**现象**：沙箱内的生成代码执行 `open(r'<工程目录>/hacked.txt','w').write('x')`，
**文件真的落到了服务器磁盘上**（实测 `ls` 确认，非推测）。

**为什么高危**：

1. **攻击者是外部用户。** 本服务开放注册，生成代码由 LLM 按**用户输入**产出。
   任何注册用户只要让模型写出这几行，就能让服务端在磁盘上落文件。
2. **可升级为远程写文件。** 服务同时托管前端静态资源，
   若写入路径落在可被 HTTP 静态路由回读的位置，就等于**远程写文件**。
   再配合"能写 Python 文件"这一点，可进一步尝试升级为代码执行。
3. **它此前完全不在防护范围内。**

**根因**：原实现只给「读」加了黑名单（拦 `.env` / `*.db` / `.ssh` / `.venv` 等
**已知**敏感路径），**写入侧没有任何对应防护**。

这是一个**模型层面的设计缺陷**，不是某一行代码写错：

- 黑名单的固有缺陷是「**没想到的就漏**」—— 磁盘上可写的路径无穷多；
- 而且人在设计"文件系统防护"时，脑子里的默认语义是"**别读秘密**"，
  **写**这个方向很容易被整体遗漏。

### 11.4 修复：写入侧从黑名单翻转成白名单

核心设计变更（`app/execution/_runner.py`）：

| 方向 | 模型 | 理由 |
|---|---|---|
| **读** | 黑名单（默认放行 + 枚举禁止） | GEE 工具链要读 matplotlib 字体、certifi 证书、torch 权重，白名单维护不过来；而读侧敏感目标（凭据/密钥/数据库）**可枚举** |
| **写** | **白名单**（默认拒绝 + 只放行 temp） | 进程**没有任何正当理由**去写沙箱临时目录以外的路径；白名单让"漏"的方向变成**拒绝**（安全） |

新增 `_set_write_roots()` / `_write_reason()`，白名单根目录 = `WB_SANDBOX_TMP` + `tempfile.gettempdir()`。

**必须覆盖每一个入口**（CPython 里同一能力有多条并列路径，漏一条前功尽弃）：

- `builtins.open` —— 判 mode 是否含 `w`/`a`/`x`/`+`
- `io.open`
- `io.FileIO` —— 裸底层类，直接构造可绕过所有包装
- `os.open` —— 按 `O_WRONLY`/`O_CREAT`/`O_TRUNC`/`O_APPEND` 标志位判定
- `pathlib` —— 走 open 底层

**附带修复目录列举**：`os.listdir(backend/)` 原本会把 `.env`、`app.db`、`.db_backup`
的**文件名**交出去。文件名 ≠ 内容，但它**精确告诉攻击者该读哪个文件**，
是踩点的第一步。改为**过滤返回值**（`os.listdir` 逐条过滤、`os.scandir` 在迭代时过滤）。

### 11.5 修复验证（每一步都真跑，非推演）

| 验证项 | 结果 |
|---|---|
| 渗透测试 v2（读 3 + 写 6 + 放行 1） | **10/10** 符合预期（写侧 6/6 全拦，temp 写正常放行） |

**特别说明「无残留对账」这一步**：状态码返回 `BLOCKED` 也可能是
「先写出去了才报错」。所以每个写用例都指定具体路径，跑完逐一对账文件是否存在

### 11.6 沉淀的守卫与教训

**回归守卫**：`tools/test_sandbox_fs.py` 新增 3b 组（15 项），
把每个穿透项都写成永久断言。这类回归**没有任何功能性症状**

**四条教训**：

1. **黑名单只能防「已枚举」的威胁。** 安全边界应按**能力白名单**设计，

2. **补防护时读写必须分开建模。** 只补了读，写就是敞开的 —— 因为人脑里
   "文件系统防护"默认指"别读秘密"。
3. **防护写完必须跑对抗性测试，且要逐个入口试。** 同一能力在 CPython 有
   多条并列入口（`io.FileIO` 裸构造就绕过 `builtins.open`）。
4. **判定"不致命"前先想清楚信息价值。** 泄漏**文件名**也是泄漏。

### 11.9 第三轮：硬链接绕过 —— 本轮**最严重**的一个漏洞

**这一项不是"同类补漏"，而是一次独立的、性质不同的穿透。**

**发现过程**：在审计「还有哪些能力能产生同一类后果」时，
问到"能不能不写文件、也不用被拦的入口，却读到被拦的文件"。
链接（link）是这类问题的经典答案，于是实测：

```python
os.link(r"<backend>\.env", r"<temp>\x.txt")   # 硬链接创建成功
open(r"<temp>\x.txt").read()                   # 读出了 .env 的明文
```

**实测结果（原始输出，非推演）**：

```
HARDLINK_OK
# 复制本文件为 .env 并填入真实值
DEEPSEEK_API_KEY=sk-<已脱敏：32 位十六进制凭据>
```

> **脱敏说明（2026-09-20）**：此处原本贴的是攻击**实测**读出的真实密钥明文。
> 项目准备开源到 GitHub，故整份文档已做脱敏处理 —— 只保留
> `sk-` 前缀与结构，具体字符一律替换。
> **这个漏洞的真实危害由"能读到明文"这件事本身证明，不需要把明文留在文档里。**

**根因**：`_sensitive_reason()` 检查的是**路径字符串**。
而硬链接与它的目标是**文件系统层面的同一个 inode** ——
路径是全新的、无害的、完全没被枚举到的，所以路径检查天然看不见它。
`os.path.realpath()` 也解析不出这条关系（硬链接没有"目标路径"这个概念，
只有软链接才有）。

> **要区分软链接与硬链接**：
> 软链接是一个**存着目标路径的特殊文件**，`realpath` 能可靠解析 → 路径检查有效；
> 硬链接是**同一个 inode 的另一个名字**，没有"目标"可解析 → 只能用 inode 比对。

**为什么这一项比前两项更严重**：
① 前两项（写文件、删文件）危害的是**服务端文件的完整性**，
   攻击者要造成业务损失还需要下一步动作；
   这一项直接泄露 **`DEEPSEEK_API_KEY` 明文** —— 拿到密钥即可盗刷 API 额度。
② 更关键的是，这个漏洞**恰好架在上一轮修复的正中间**：
   11.4 刚把"读"用黑名单封好、11.8 刚把"写"用白名单封好，
   而硬链接**既不是读也不是写** —— 它在一个第三类入口上，
   把两套模型的成果一次性绕过。

**修法（两重）**：

| 层 | 手段 | 作用 |
|---|---|---|
| 阻断 | `_block_link_creation()` 封禁 `os.symlink`/`os.link`/`os.symlinkat`/`os.linkat` | 沙箱内**一律不许创建链接**（正向需求为零，误伤风险为零） |
| 兜底 | `_hardlink_reason()` 用 `(st_dev, st_ino)` 与预扫描的敏感文件 inode 表比对 | 即便链接已在沙箱外被创建，凭 inode 仍能识别并拒绝 |

`_collect_sensitive_inodes()` 在加固开始前遍历 backend 目录（深度 ≤ 2），
把 `.env*`、`*.db`、`*.db_backup`、`*.key`、`*.pem` 等已知敏感文件的 inode 记下来。

**⚠️ 修复过程中自己引入并踩到的坑（值得写下来）**：

`_hardlink_reason()` 里一开始写的是 `os.stat()`，而 `os.stat` **本身已被替换成 guard**，
guard 里要调 `_sensitive_reason()`，`_sensitive_reason()` 末尾又要调 `_hardlink_reason()`
→ **无限递归**。

症状不是干脆的报错，而是：
1. 先抛 `RecursionError`；
2. 紧接着**沙箱子进程卡死到外层超时**，表现为「整个测试挂住不返回」；
3. 日志为空（子进程没能输出结构化结果），最终被 SIGTERM 杀掉。

**定位手法**：用 `python -u`（无缓冲）+ `head -40` 才看到被打断前的 `FAIL:RecursionError`。
**修法**：在所有替换动作**之前**缓存 `_raw_stat = os.stat`，
`_hardlink_reason()` 与 `_collect_sensitive_inodes()` 一律改用 `_raw_stat`。

> **教训**：给标准库函数打补丁时，guard 自身**绝不能再调用被自己替换掉的原名**。
> 必须提前缓存原始引用。而且这类错误的表现是**挂起**而非报错，极难定位。

**验证**：

| 项 | 结果 |
|---|---|
| 硬链接攻击复现（原路径重放） | **泄露 0/3，全部拦住** |
| 拦截信息 | `BLOCKED_AT_LINK: 沙箱安全策略禁止创建链接（os.link）` |
| `os.symlink` / `os.chdir` / `os.putenv` / `os.unsetenv` / `os.setuid`（3d 组 15 项） | **全部 BLOCKED**（`setuid` 在 Windows 上为 `AttributeError`，天然不可用，判为同等安全） |
| **关键对账**：`.env` 原文未被读取（以 inode 表 + 复现攻击双重验证） | **完好** |
| 无残留：链接文件 / `_pen_*` / `hacked*` / `leak.tmp` | **无残留** |
| 单文件总计 | **76/76**（12s，无性能退化） |
| 全套回归 | **354/354**（auth 28 + isolation 83 + sandbox_fs 76 + sa_route 44 + static_route 57 + no_stale_year 22 + field_crypto 39） |
| `gee_doctor --self-test` | **9 OK / 0 FAIL** |
| **真实 GEE 终检 2** | 北京市土地分类 `succeeded` **54.3s / attempts=2**，3 图层 + 2 图表 + 9 类占比，建成区 63.74% |

**性能守恒**：新增的 `_collect_sensitive_inodes()` 全量扫描实测 **0.012s**，
`test_sandbox_fs.py` 全套 12s（加固前 10s），可忽略。

**至此 11.7 的两条剩余风险，① 已闭环，② 属架构级限制。**

### 11.10 三轮修复总览

| 轮 | 漏洞 | 危害 | 穿透原理 | 修法 |
|---|---|---|---|---|
| 1 | 写入侧无防护 | 可在服务端任意落盘 | 黑名单"没想到的就漏" | 写侧翻白名单，覆盖 5 入口 |
| 2 | 破坏性操作整组漏掉 | 可删/改服务端真实文件 | 只修"写"漏了同类不同入口 | `_guard_destructive()` 覆盖 os 12 + shutil 6 |
| 3 | **硬链接绕过** | **泄露 API 密钥明文** | 路径检查看不见同 inode 的另一个名字 | 禁建链接 + inode 比对兜底 |

**三次修复共同证明的一件事**：这三次都不是"代码写错了"，而是
**安全模型选错了 / 能力清单不完整**。
所以真正有效的动作不是逐条打补丁，而是：
① 写侧用白名单（失败方向落在"拒绝"）；
② 修完一类危害后，回头枚举**还能以什么别的途径造成同样后果**；
③ 每类修复都必须配一条**不可绕过的回归守卫**（本项目为 `test_sandbox_fs.py` 76 项）。

## 十二、接口契约复评（2026-09-20 下午 · 参数回显缺口）

### 12.1 怎么发现的

用户问「还需要做哪些任务」时，没有凭记忆列清单，而是**重新查了生产库**，
并把 `GET /api/tasks/{tid}` 的返回字段与提交请求体**逐字段比对**。

这个比对手法直接暴露了一处不对称：**提交时填了什么，读回来并不完全一致。**

### 12.2 缺口内容

`GET /api/tasks/{tid}`（`app/main.py:573`）返回了
`region / task_type / start_date / end_date / feedback` 等，
**唯独漏了 `cloud_threshold`。** 这个值提交时是要用户填的。

**三处连带影响**：

| # | 表现 | 位置 | 严重度 |
|---|---|---|---|
| ① | 前端「重新运行」读 `t.cloud_threshold ?? 20` → 字段不存在 → **永远退回默认 20** | `App.jsx:503` | **功能错误**：用户改了云量再重跑，静默跑回默认值 |
| ② | 报告导出渲染成「云量阈值：%」 | `main.py:631` | 读者分不清是"没填"还是"程序坏了" |
| ③ | 用户无法在任务详情里核对自己填的参数 | 前端详情区 | 可核对性缺失 |

**根因不是查询问题**：`store.get()` 用的是 `SELECT *`，值**一直都在手里**，
只是序列化时没往外投影。**值取到了但没返回**，是纯粹的契约遗漏。

> 这跟「冻结年份」「列表静默截断 50 条」是**同一类缺陷**：
> 数据层是对的，接口层漏了一环，然后下游全部静默走默认值。
> 这类 bug 的共同特征是 **不报错、不崩溃，只是悄悄用了错的值**。

### 12.3 修复

**后端（2 处）**
- `main.py` `get_task()` 返回体加 `cloud_threshold`
- `task_store.py` `list()` 的 SELECT 补 `start_date / end_date / cloud_threshold`
  （列表页与「批量重跑」也依赖它）

**前端（1 处）**
- `App.jsx` 任务详情区新增参数回显行（区域 · 时间范围 · 云量）

**格式化（2 处，修 bug 时顺带发现的同类问题）**
该列在 SQLite 里是 `REAL`，直接插值会渲染成 `37.0%`。
报告用 `:g`、前端用 `Math.round()`，统一为整数百分比 —— 与提交表单口径一致。

**「未记录」而非留空**：取不到时写「未记录（历史任务或未指定）」，
不留空。因为 `f"...{''}%"` 会渲染成「云量阈值：%」，看起来像故障。

### 12.4 验证（新建 `tools/test_task_echo.py`，22 项）

契约测试的核心断言是 **`回显值 == 提交值`**，并刻意用 **37**（非默认 20）
提交 —— 这样"退回默认值"这个具体故障模式会被直接抓住。

| 组 | 项 | 结果 |
|---|---|---|
| 详情接口 | 含 `cloud_threshold` / 等于 37 / 未被默认 20 覆盖 | 3/3 |
| 其余参数 | region / start_date / end_date / task_type 回显 | 4/4 |
| 列表接口 | 含该字段 / 等于 37 / 含日期 | 4/4 |
| 报告导出 | 含「云量阈值：37%」/ 无浮点尾巴 / 无空值 | 3/3 |
| 隔离性回归 | 他人访问返 404 不返 403 | 1/1 |
| 环境自检 | 服务就绪 / **库文件确实建在预期路径** | 2/2 |

**「库文件确实建在预期路径」这条断言是刻意加的**：
本项目有过血案 —— 传 Git Bash 风格路径给 Windows Python，
会静默在 `C:/c/...` 新建空库，而测试自身断言依然全绿（典型的假绿）。
这条断言是**防止测试台自己骗自己**。

### 12.5 我自己踩的两个坑（都记在测试文件注释里）

**坑 1：轮询漏传 Cookie**
首版轮询 `GET /api/tasks/{tid}` 时忘了带 cookie，
`_own_task_or_404` 把所有请求判成 404，循环跑满 120 次后 `task` 只剩
`{"detail": "任务不存在"}` → **后面所有字段断言全 fail**。
症状极像"字段没投影"，我差点去改后端 —— 实际是测试脚本自己的锅。
**教训：字段断言全挂时，先确认请求真的成功了（加一条"拿到任务且非 404"的断言）。**

**坑 2：结果行格式不符合回归脚本约定**
写成 `结果：22 通过 / 0 失败`，而 `regress_all.sh` 用
`grep -oE '[0-9]+/[0-9]+ *通过'` 抓最后一行 → **解析不到 → 判成"套件没全绿"**，
即使实际 22/22 全过。已改为 `结果：22/22 通过`。

### 12.6 失败率监控（把 7.6% 变成会主动报警的东西）

**为什么做**：实测日失败率 09-15→09-20 为
`0% / 5.9% / 6.9% / 13.3%`，但**没有任何机制会主动告诉你它在涨** ——
只能靠人工查库才发现。这跟"沙箱悄悄失效"是同一类问题：
**没有症状的系统性退化**。

**实现**（`demo_doctor.py` 新增 L9）：
- 把 `[(status, created_at)]` 切成「近 24h」与「此前」两段算各自失败率
- 判定逻辑抽成**纯函数** `_failure_rate_state()`，便于自检直接喂数据
- **先卡样本量再卡比率**：`n < 5` 时只给 WARN 不算失败 ——
  否则 2 条错 1 条（50%）会天天误报
- 分级：近期 ≥30% → FAIL；较历史翻倍且 ≥15% → WARN；其余 OK

**对当前生产库的真实输出**：
```
[L9 失败率趋势]
  [ OK ] 失败率未见异常
         全期 66 条 / 失败 5 条 = 7.6%
         近 24h 15 条，失败率 13.3%（历史 51 条 5.9%）
```
13.3% 未触发报警是**正确行为**：样本仅 15 条，未达 30% 红线。
如果它在这种情况下报警，我反而要怀疑规则太钝。

**自检从 17 项扩到 40 项**，新增 7 项覆盖切段与比率边界
（全成功 / 无历史 / 两段分离 / 恶化识别 / 空库 / 小样本）。

### 12.7 复评结论

| 项 | 修前 | 修后 |
|---|---|---|
| `cloud_threshold` 回显 | ❌ 缺失 | ✅ 详情 + 列表 + 报告 |
| 「重新运行」参数 | 静默退回默认 20 | 沿用原值 |
| 报告云量显示 | 「云量阈值：%」 | 「云量阈值：37%」 |
| 失败率可见性 | 只能人工查库 | `demo_doctor` L9 自动判定 |
| 契约守卫 | 无 | `test_task_echo.py` 22 项 |
| 全套回归 | 354/354 | **371/371** |

**这一节的价值不在于修了一个字段，而在于找到了一种审计手法**：
**把「提交请求体」与「读取响应体」逐字段比对。**
它不需要读代码就能定位契约缺口，且能直接抓到"静默走默认值"这类最难发现的缺陷。
