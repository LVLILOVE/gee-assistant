## 第 2 轮抓到的真实缺陷（已修）

失败用例：`e2e-classification-长三角`（任务 `140f1a9f66c4`，attempts=3，执行 132.0s）

```
[生成] 代码来源=deepseek
[执行] 第 1 次失败 [gee]：AttributeError: 'Image' object has no attribute 'mode'
[调试] 错误分类=gee，请求大模型修复代码
[执行] 第 2 次失败 [gee]：AttributeError: 'Image' object has no attribute 'mode'
[调试] 错误分类=gee，请求大模型修复代码
[执行] 第 3 次失败 [gee]：AttributeError: 'Image' object has no attribute 'mode'
[结束] 已达重试上限（3 次），建议人工介入修改
```

**3 次错误信息逐字相同** —— 这不是"修了没修好"，而是自动调试**没能产生有效改动**。
根因是两层：

1. **生成侧知识缺口**：`ee.Image` 根本没有 `.mode()`（它是 ImageCollection 的方法）。
   模型写了 `img.select('label').mode()` 求众数类别，属 GEE API 幻觉。
2. **调试侧位置误导**：traceback 把 `<gee_code>` 帧定在第 133 行
   `ee.List(months).map(monthly_class_stats)` —— 而**这一行本身完全正确**，
   真正的缺陷在被 `.map()` 的那个函数体里。只给"第 133 行"，
   等于把模型引去改一行没问题的代码，于是三轮原地打转。

修法（三处）：

| 位置 | 改动 |
| --- | --- |
| `app/codegen.py` `_RESOURCE_RULES` 规则 k | 写清 Image 与 ImageCollection 的方法不通用、`.mode()` 的正确两条写法、以及"`.select()/.clip()` 之后仍是 Image" |
| `app/debugger.py` 新增 `callback_note()` | 识别"出错行是 `.map()`/`.iterate()` 调用"，明说位置是调用点不是缺陷点，并把**被 map 的函数体完整抠出来**放进修复提示 |
| `app/orchestrator.py` `_node_repair()` | 检测"修复后代码与上一次完全相同"，记日志并给下一轮附加强提醒，避免静默白烧一轮 |

**修后复验**：同一用例重新提交 → **首次执行即成功**（`attempts=1`，执行 105.7s），
不再需要自动调试介入。

> ⚠ 但必须说清：这次复验是 **1 次**。LLM 生成本身有随机性 —— 该用例第 1 轮成功、
> 第 2 轮失败、修后 1 次成功。正确说法是"规则 k 关掉了这类错误的一个已知来源"，
> **不能**说"这个用例已经稳定通过"。要得到稳定结论只能多跑几轮。

## 口径与方法

- **中位数定义**：`statistics.median`，即偶数个样本取中间两个的均值。
  （早期版本写成 `lat[len(lat)//2]`，对偶数样本取的是**上中位数** —— 第 1 轮真实中位数
  47.5s 被算成 56.5s。方向上是在苛待自己，但口径不标准、验收方一算就对不上，
  已修正并加入自检断言 `偶数样本取标准中位数 47.5`。）
- **耗时口径**：`finished_at - started_at`，即真实执行时长（不含排队）。
- **一次执行成功率**：按 `attempts == 1` 判定（首次即成功、未触发自动调试）。
- **单轮即样本**：端到端每条要烧 30-100s 真实 GEE 计算且受任务配额限制，
  单轮 8 条只是样本。**引用这些数字必须说明轮次**。
