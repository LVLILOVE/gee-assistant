### T1（**已修**）绑死版本号的浏览器路径 → 整套无障碍与截图校验静默失效

**现象**：`--with-a11y` 时两个套件都只报 `没解析到结果行`，日志尾部是一句
`FileNotFoundError: [WinError 2]`。

**真因**：两个套件里写着

```
C:\Program Files (x86)\Microsoft\Edge\Application\153.0.4234.48\msedge.exe
```

而 Edge 自动更新后该目录被改名成 **`153.0.4234.48.deleting`**。现场 `ls` 一眼可见：

```
151.0.4129.101                           ← 有效
151.0.4129.107.deleting
152.0.4191.66.deleting
153.0.4234.32.deleting
153.0.4234.48.deleting                   ← 代码里写的就是这个
154.0.4258.37                            ← 当前实际版本
```

**为什么这是缺陷而不只是"环境问题"**：它**不是校验失败，是压根没跑**。
而这两个套件只有显式 `--with-a11y` 才执行，于是"无障碍校验层已整体不可用"
这件事长期无人发现。这与 `test_no_stale_year.py` 守的是**同一类错误**：
把当时有效的环境值固化进代码。

**关键手法：用"同一批硬编码"扫全仓库找全同类，而不是修一个点。**
扫出 **5 个文件**（2 个无障碍套件 + 3 个截图脚本）：

| 文件 | 用途 |
|---|---|
| `tools/test_a11y_contrast.py` | 对比度实测（CDP 取计算样式） |
| `tools/test_a11y_kbd.py` | 键盘可达/焦点可见/减少动效/触控目标 |
| `tools/_shot_ui.py` | 登录页 + 主界面截图 |
| `tools/_shot_focus.py` | 聚焦截图（滚动右栏分别拍图表/图例/结论卡片） |
| `tools/_shot_result.py` | 跑一条离线任务后截结果区 |

> 只修那两个套件，就是典型的**"补一个点、漏一个面"**（本项目在 GEE 空集合那次
> 已经吃过一次同样的教训：只给 `change_detection` 加守卫，另外三种口径一条没有）。

**修法**：新增 `backend/tools/_browser.py` → `find_edge()` 作为**单一定位入口**：

1. `shutil.which("msedge"/"chrome"/"chromium")`（最通用）
2. Edge 的**无版本号稳定入口** `Application\msedge.exe`
3. Chrome 的稳定入口
4. 兜底：扫 `Application\<版本号>\`，**显式跳过 `.deleting`**，取版本号最大者

找不到时按项目既有约定处理：打印 `跳过：未找到 Edge/Chrome 浏览器…` 并 `exit 0`
（缺环境前置不是产品缺陷），由 `regress_all.sh` 记入"已跳过"而**不是**"未通过"。

**验证（实测，非推断）**：
- `python tools/_browser.py` → 命中 `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.EXE`
- `test_a11y_contrast.py`：修前"秒崩"，修后 **10/10 通过**（真浏览器登录线上实例、
  按 WCAG 公式逐个量计算样式，最小对比度 4.91:1）

**守卫**：`test_audit_regressions.py` **I 段**扫**全部** `tools/*.py`（26 个）里的
**字符串字面量**，正则要求同时满足"带引号 + 盘符 + 含版本号目录 + `.exe`"，
并逐个断言 5 个文件都用了 `find_edge()`。
> ⚠️ 反面样本（`_browser.py` 的文档、守卫自身的注释）**必须去掉引号**，
> 否则会被自己扫中 —— 这条已写进代码注释。

### T2（**已修**）回归脚本解析不了 shell 套件的汇总行 → **假红**

`--http` 的三个 shell 套件输出的是

```
结果：41 通过，0 失败，2 跳过      （test_auth_http.sh）
结果：49 通过 / 0 失败             （test_isolation_http.sh / test_quota_http.sh）
```

而 `regress_all.sh` 只认 `N/M 通过`。结果：**零失败的套件全部被判 ❌**，
汇总显示"3 个套件没全绿"。

**为什么这值得修**：它不会漏掉问题，但它会把**绿色运行说成红色**。
久了人就开始无视红色 —— **假红比假绿更难治**，因为它摧毁的是"红色=有事"这个信号。

**修法**：解析器加一条等价格式回退：
`N 通过` + `M 失败` → `N/(N+M) 通过`（跳过项不计入分母，与既有语义一致）。
另补 `跳过：` 前缀通道（见 T1）。

**验证**：回测已有日志 → `41/41`、`49/49`、`27/27` 全部解析成功；
随后一次真实全量回归里三个套件**全部显示 ✅**（此前恒为 ❌）。

### T4（**已修**）无障碍键盘套件连拍截图中途挂死 —— 真因是**响应被丢弃**，不是渲染器卡死

**现象**：`test_a11y_kbd.py` 的"焦点可见性"检查靠 before/after **截图像素比对**
（因为 antd 用 `box-shadow` 画焦点环，读 `outline` 属性必然误判）。
连拍若干张后，**某一次** `Page.captureScreenshot` 不再返回。

**上一轮的结论是"永不返回、原因不明"**（socket 超时 30s → 抛错；改到 150s 仍不返回，
整轮跑了 3m51s），于是只在代码里留了注释 + 可读失败信息。
**本轮用三轮诊断脚本查到了真因。**

**真因**：headless Edge 会**偶发丢弃**某一次截图请求的响应。判定依据是三条现场证据：

| 证据 | 观测 |
|---|---|
| 挂住时**连接是否还活着** | 同一条连接上 `Runtime.evaluate` 正常返回；`recv()` 静默（对端不关连接） |
| 把**同一条请求原样重发** | **立刻成功**（观测 3/3） |
| 丢弃率 | 同一轮内按时间顺序：整页 **0/30** → 夹 Tab/blur **1/30** → clip 小图 **2/20**，**随会话活动量上升** |

由此可以解释上一轮两个"反直觉"的现象：
- **加超时没用**：丢掉的响应等多久都不会来 —— 所以 150s 与 30s 结果一样；
- **补上 `Page.enable` 后"能多撑几站"**：那只是把随机命中推迟了，**不是修复**。

**已排除的 5 个假设（都实测过，别再重试）**：`fromSurface: False` /
`Page.bringToFront` + `Target.activateTarget`（后者在**页面级**会话上会被 CDP 拒掉，
而 `call()` 只看 `id` 不看 `error` → 静默变成一个空操作，这种"假修复"最骗人）/
改用 `/json/list` 复用前台标签页 / 加长超时 / **减小载荷**
（clip 小图同样会丢 → 丢弃与载荷大小无关）。

**修法**（两处，缺一不可）：
1. `shot()` 改成**有界重试**（4 次 × 8s）。短超时是刻意的：单次等 45s 换不来成功，
   只会把故障拖长；
2. 焦点比对改用 `clip` **只截元素周边一小块** —— 载荷 55KB → ~8KB，而且
   `scale` 直接按 dpr 出图，**不必再手工乘 `devicePixelRatio`**。那个手工乘法正是
   更早一次误判的元凶：dpr=1.25 时裁剪框整体错位，明明有焦点环却裁成旁边空白
   → 变化像素 0 → 误报"无焦点指示"。

顺带两处加固：重试到上限仍拿不到图时**如实记账**（计入 `unresolved` 并报失败，
而不是当成"没有焦点指示"）；再加一条**反静默断言** —— 若所有位置的变化像素都是 0，
就判"判据本身可能失效"，避免将来 clip 裁错位置时静默给出反的结论。

**验证**：整套跑通 **5/5 通过**，输出里带一句
`[注] 期间有 5 次截图响应被浏览器丢弃，已自动重发成功` ——
这行本身就是修复生效的证据，也顺带把"丢弃率有多高"留成了可观测数据。

### T6（**已修**）界面让用户"点「重新运行」"，但**这个控件根本不存在**

**现象**：`MapPanel` 的提示文案写着「点「重新运行」重跑一次该分析即可刷新图层」，
另一处写着「可重新运行该分析以获取定位信息」。**把整个前端搜一遍，"重新运行"
只出现在这两句文案里** —— 没有按钮、没有任何入口。

**为什么这比不提示更糟**：文案指了一个不存在的东西。用户会去找、找不到，
然后把"这个界面坏了"当成结论。而这恰好发生在本项目最忌讳的场景里 ——
栅格图层的 `tile_url` 内嵌 GEE 签发的**短期令牌**，历史任务放一会儿图层就失效、
色块全无；此时用户唯一的出路就是重跑，**而重跑入口不存在**。

**根因**：令牌只能由 GEE 在**重新计算时**签发，没法凭空续期（我们没有存下可复用的
EE Image）。所以"按原参数重跑"不是可选项，是这条链路**唯一能自愈的动作**。

**修法**：

## 五、专项：瓦片加载失败此前**完全静默**（F10）

**现象**：打开历史任务，地图只有底图、**没有任何色块**，界面不给任何提示。

**证据链（实测）**：
1. GEE 签发的 `tile_url` 里嵌的是**短期令牌**；任务把该地址原样存库，几天后失效。
2. 后端代理把上游 4xx 统一映射成 400。现场实测无效 mapid：
   ```
   GET /api/tile/6/52/24  →  HTTP 400
   {"detail":"瓦片请求被拒绝：GEE 返回 404"}
   ```
   （并行排查另查到上游 `401 Invalid token`，`/api/tile` 87 次请求**全部 400**，
   而 `/api/basemap` 全部 200 —— 即底图正常、分析图层全灭。）
3. 前端**没有任何 `tileerror` 监听**，Leaflet 拿不到图只把瓦片留成灰色。

**为什么这是真缺陷而不只是"不方便"**：用户看到一张没有色块的地图，唯一能得出的结论是
**"分析错了地方 / 分析没结果"** —— 而这恰恰是本项目历史上最忌讳的失败形态
（参见地图定位那次"恩施大峡谷显示成苏州"）。**错误的自信比明确的失败危险得多。**

**修法**：栅格图层挂 `tile.on('tileerror', ...)`，累计失败数后提示
「栅格图层有 N 张瓦片加载失败（图层名）…… 最常见原因是 GEE 图层链接里的短期令牌已过期
（历史任务放久了都会出现），点『重新运行』重跑一次即可刷新图层。」

两个刻意的设计取舍：
- **去抖 400ms**：一次地图加载会并发几十张瓦片，逐张 `setState` 会造成渲染风暴。
- **不给底图挂**：底图在远洋区返回 204（正常留空），会被判成加载失败造成误报。

### 9.4 过程中踩到的四个坑（都已写进代码注释）

1. **vitest 在被管道接走时仍输出 ANSI 转义**，汇总行实际是
   `\x1b[2m      Tests \x1b[22m \x1b[1m\x1b[32m10 passed\x1b[39m` ——
   于是 `grep -oE 'Tests  [0-9]+ passed'` **永远匹配不到**，计数静默变成 `0/0`。
   反向验证脚本的第一版就因此给出了"修复前也没红"的**假结论**。
   这与 T2 是**同族错误**：判据与输出格式不匹配。修法：`--no-color` + 再剥一遍转义。
2. **RTL 的 `waitFor` 认不出 vitest 的假定时器** —— 它判断的依据是
   `typeof jest !== 'undefined'`，而 vitest 全局里没有 `jest`，于是它以为在用真定时器，
   内部的 `setInterval` 被 sinon 接管后永不触发 → **启用假定时器的用例一律 20s 超时**。
   修法：不依赖 `waitFor`，改用纯微任务冲洗 + 直接查 DOM。
3. **antd 会给"恰好两个汉字"的按钮文案插空格**（`登录` → `登 录`、`退出` → `退 出`），
   按可访问名精确匹配会找不到元素。
4. **判据自己会坏，而且坏了测试是全绿的**：F7 那条最初写的是 `queryByText(示例文本)`，
   而**示例标签**里有一个字符串与它逐字相同 —— 对话被清空后示例标签会重新出现，
   于是**把"已清空"判成了"没清空"**。改成按 `.chat-msg.user` 这类元素判定，
   并补了一条反面确认（断言示例标签确实回来了）。
   > 同族风险：任何"整页未渲染"也会让 `queryByXxx(...).toBeNull()` **假通过**。
   > 所以每条"不该存在"的断言，都尽量配一条"该存在"的确认。
