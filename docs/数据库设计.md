## 1. 设计概述

- **选型**：SQLite 3，单文件、零配置，契合任务书要求与本地化部署场景。
- **存储内容**：用户信息、会话/任务记录、任务代码、执行结果元数据、常用区域。
- **并发策略**：`threading.Lock` 保证写操作串行化；连接 `check_same_thread=False`。

## 2. 现有表结构（已实现）

### 2.1 tasks（任务表）

存储每次分析任务的完整信息与结果。

| 字段 | 类型 | 说明 |
|---|---|---|
| task_id | TEXT (PK) | 任务 ID，`uuid4().hex[:12]` |
| status | TEXT | pending / running / succeeded / failed |
| task_type | TEXT | ndvi / water / classification / change_detection |
| region | TEXT | 分析区域描述 |
| start_date | TEXT | 起始日期 YYYY-MM-DD |
| end_date | TEXT | 结束日期 YYYY-MM-DD |
| cloud_threshold | REAL | 云量阈值（0-100） |
| code | TEXT | 生成的分析代码 |
| result | TEXT (JSON) | 执行结果（图层/图表/错误），序列化 `ExecutionOutcome` |
| logs | TEXT (JSON) | 执行日志列表 |
| attempts | INTEGER | 自动调试尝试次数 |
| created_at | REAL | 创建时间戳（epoch 秒） |
| user_id | INTEGER | 归属用户，关联 users.id；**`0` = 无主**（历史数据，或鉴权关闭时创建） |

> `user_id` 由服务端在 `POST /api/tasks` 时从会话写入，**不接受客户端传值**（模型里没有这个字段）。
> 查询时传 `None` 表示"不按用户过滤"，生产代码总传具体 id。

### 2.2 regions（常用区域表）

| 字段 | 类型 | 说明 |
|---|---|---|
| name | TEXT (PK, 联合) | 区域名称 |
| user_id | INTEGER (PK, 联合) | 归属用户；`0` = 无主 |
| lon | REAL | 中心经度 |
| lat | REAL | 中心纬度 |
| desc | TEXT | 描述 |
| created_at | REAL | 创建时间戳 |

> 内置的 13 个区域定义在 `backend/app/regions.py` 的 `REGION_LIBRARY`，不落库；仅自定义区域写入本表。
>
> **为什么主键是 `(name, user_id)` 而不是 `name` 单列**：单列主键下
> `INSERT OR REPLACE` 会让「B 保存一个与 A 同名的区域」直接**替换掉 A 那一行** ——
> 坐标变成 B 的、`user_id` 也变成 B，A 的区域从自己列表里凭空消失且再也删不掉。
> 这是真实的跨用户数据破坏，所以改成联合主键让同名区域各自共存
> （不同用户可以各有一个"研究区"，互不可见、互不影响）。

### 2.2.1 关于"无主"为什么用 `0` 而不是 `NULL`

`tasks.user_id` 不参与主键，本来用 `NULL` 也无妨；但 `regions` 与 `user_settings` 的
`user_id` **在联合主键里**，而 SQLite 的主键列**允许 `NULL`** ——
`(名称, NULL)` 不触发唯一冲突，于是同一用户反复保存同名区域会插出重复行，
`INSERT OR REPLACE` 也替换不掉。

为了不让同一套代码里出现两种"无主"，三张表统一：**`0` = 无主 / 全局默认值**。
写入前由 `_norm_uid()` 归一，库中不再存在 `NULL` 归属。

### 2.3 users（用户表，注册登录）

`backend/app/auth.py`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER (PK) | 自增主键 |
| username | TEXT (UNIQUE) | 用户名，3–32 位 |
| password_hash | TEXT | PBKDF2-HMAC-SHA256，20 万次迭代，十六进制 |
| salt | TEXT | 每用户独立随机盐，16 字节十六进制 |
| is_admin | INTEGER | 1=管理员；首个注册用户自动置 1 |
| created_at | REAL | 创建时间戳 |

> 密码只存哈希，永不落明文；哈希用标准库 `hashlib.pbkdf2_hmac`，不引入 bcrypt/passlib
> （本机装包链路不稳定，为一个哈希函数去赌一次 pip 不划算）。

### 2.4 sessions（会话表）

| 字段 | 类型 | 说明 |
|---|---|---|
| token | TEXT (PK) | `secrets.token_urlsafe(32)` 随机串 |
| user_id | INTEGER | 关联 users.id |
| created_at | REAL | 创建时间戳 |
| expires_at | REAL | 过期时间戳（默认 7 天） |

> **为什么用服务端会话表而不是 JWT**：token 存服务端才能"立即失效"——
> 注销、改密码都能瞬间踢掉会话；JWT 在过期前无法吊销，泄露后只能等它自然失效。
> 索引 `idx_sessions_user` 支撑"按用户批量清会话"和过期清理。

### 2.5 user_settings（用户设置 / 分析偏好）

| 字段 | 类型 | 说明 |
|---|---|---|
| key | TEXT (PK, 联合) | 设置名，如 `analysis_preferences` |
| user_id | INTEGER (PK, 联合) | 归属用户；**`0` 表示全局默认值** |
| value | TEXT (JSON) | 设置值 |
| updated_at | REAL | 更新时间戳 |

> 联合主键 `(key, user_id)`。用 `0` 而不是 `NULL` 表示"全局"，是因为它参与主键，
> 而 SQLite 的主键列允许 `NULL`，会导致 `(key, NULL)` 出现重复行。
>
> 读取时**全局优先叠加用户私有**：`get_settings(user_id)` 先取 `user_id=0` 的行，
> 再用该用户自己的行覆盖。所以新用户天然能继承全局默认值，而一旦设了私有值就只认自己的。

### 2.6 结构迁移（旧库自动升级）

`TaskStore._init_db()` 每次启动都会跑 `_migrate()`，幂等。处理顺序不能调换
（先把主键改对、再归一 `NULL`，否则后一步的比较条件会漏掉还没归一的 NULL 行）：

| 顺序 | 情况 | 处理 |
|---|---|---|
| 1 | `tasks` 缺 `user_id` | `ALTER TABLE ADD COLUMN`，老行留 `NULL`（下一步会归一成 0） |
| 2 | `regions` 缺 `user_id` | `ALTER TABLE ADD COLUMN` |
| 2 | `regions` 的 `user_id` **不在主键里** | 建新表 `(name, user_id)` 联合主键 → `INSERT OR IGNORE` 迁入（`COALESCE` 归 0）→ 删旧表 → 改名 |
| 3 | `user_settings` 表不存在（全新库） | 直接按 2.5 结构建表 |
| 3 | `user_settings` 存在但缺 `user_id` | 建新表 → 老行以 `user_id=0` 迁入 → 删旧表 → 改名 |
| 4 | 还有 `NULL` 归属（上一版迁移遗留） | `UPDATE ... SET user_id=0 WHERE user_id IS NULL` |
| — | 已是最新结构 | 前三步都跳过，第 4 步的 UPDATE 影响 0 行 |

> 怎么判断"`user_id` 在不在主键里"：`PRAGMA table_info(t)` 的第 6 列 `pk` 是主键内序号，
> 0 表示不是主键成员。比去解析 `sqlite_master.sql` 的 DDL 文本稳。
>
> 老数据的归属由 `_adopt_legacy_data()`（`main.py`）一次性划给**最早注册的管理员**，
> 幂等且只动 `user_id = 0` 的行。实测 22 条历史任务全部接管，`count_unowned()` 归零。

## 3. ER 关系

```
users (用户)                     tasks (分析任务)              regions (自定义区域)
┌──────────────────┐   user_id  ┌────────────────────┐ user_id ┌─────────────────┐
│ id (PK)          │◄───────────│ task_id (PK)       │◄────────│ name  (PK, 联合) │
│ username (UNIQUE)│            │ task_type          │         │ user_id(PK, 联合)│
│ password_hash    │            │ region (文本引用)   │         │ lon / lat / desc │
│ salt / is_admin  │            │ ...                │         │ created_at       │
└────────┬─────────┘            │ result (JSON)      │         └─────────────────┘
         │ user_id (FK)         └────────────────────┘
┌────────▼─────────┐            user_settings (设置)
│ sessions         │            ┌──────────────────────┐
│ token (PK)       │            │ key (PK, 联合)        │
│ expires_at       │            │ user_id (PK, 联合)    │ ← 0 = 全局默认
└──────────────────┘            │ value / updated_at   │
                                └──────────────────────┘

user_id = 0 在三张表中统一表示「无主 / 全局默认」；> 0 表示属于该用户。
```

> 说明：任务表用 `region` 文本而非外键关联区域表，原因是内置区域不落库、且区域允许自由输入任意地名，故不做强约束。
>
> `tasks` 与 `regions` 的隔离**在应用层强制**：
> `GET /api/tasks` 只列自己的；`GET /api/tasks/{id}` 与 `/report` 不属于自己时返 **404 而不是 403**
> —— 403 会暴露"这个 ID 确实存在"，把别人的任务 ID 空间变成可探测的信息泄漏面。

落地结构与最初设想不同：没有拆成 `scientific_rules` / `expression_style` / `coding_conventions`
三列，而是用**通用的 `key` + JSON `value`**，值形如：

```json
{"instructions": "自定义指令自由文本", "data_source": "auto|sentinel2|landsat",
 "output_language": "zh", "agent_profile": "analyst|mentor|concise"}
```

> 理由：偏好的字段还在演进（画像就是从单列扩出来的），JSON 值加字段不用改表结构。
> 代价是没有列级约束，非法值靠 `get_preferences()` / `save_preferences()` 在读取时兜底纠正。

> 两条链路都带 `user_id`：`POST /api/tasks` 把归属写进任务，后台线程通过

## 6. 数据安全（对齐任务书 6.2）

- **多用户隔离已落地**：`tasks` / `regions` / `user_settings` 三张表按 `user_id` 隔离；
  越权访问返回 404 而非 403，避免通过状态码探测他人任务 ID 是否存在。（验证见《测试报告》3.13）
- 密码只存 PBKDF2 哈希 + 逐用户随机盐；GEE 凭据库用 Fernet 加密，密钥独立存 `.key`；
- GEE 凭据**不落库**，仅存服务端环境变量（`.env`）并加密；
- 数据库文件与凭据文件加入 `.gitignore`，不入版本库；
- `APP_DB_PATH` 可覆盖数据库位置，供自动化测试在临时库上跑真实迁移，不碰线上数据。

### 6.1 业务数据字段级加密（2026-09-20 落地）

PRD §7 要求「用户区域/任务描述敏感，**加密存储**」。此前这些字段是明文落盘的
（从库里直接捞一条就能读到「长江三角洲」和完整可读的 GEE 脚本）。现已加密：

| 表 | 加密字段 | 说明 |
|---|---|---|
| `tasks` | `region` / `code` / `result` / `logs` / `feedback_note` | 区域名、生成的 GEE 代码（含 AOI 坐标）、图层与统计结果、执行日志、用户反馈自由文本 |
| `regions` | `name` / `desc` | 用户自定义区域名与描述 |

**实现方式**

- 算法：Fernet（`cryptography` 库）；密钥存 `data/credentials/.data_key`（已 gitignore）。
  可用环境变量 `WB_DATA_KEY`（base64 key）或 `WB_DATA_KEY_PATH` 覆盖，便于换机部署。
- **值前缀标记法**：密文统一带 `ENC1:` 前缀。带前缀 = 已加密，不带 = 明文（历史数据）。
  这一条同时是**迁移幂等性的唯一保证** —— `encrypt_field()` 遇到已带前缀的值原样返回，
  所以迁移可重复执行而不会二次加密（二次加密 = 数据永久损坏且不可逆）。
- **加解密边界在存储层**（`task_store.py`），不在 API 或 orchestrator：
  存储层是全项目唯一读写 `tasks` 的咽喉，放这里新增调用方就不可能漏加密。
- **应用层完全透明**：`store.get()` / `list()` 读出来就是明文，前端与业务代码零改动。

**配套：`regions.name_bidx` 盲索引**

`regions.name` 是联合主键的一部分，而 Fernet 带随机 IV —— 同一明文两次加密结果**不同**，
所以 `WHERE name=?` 永远匹配不上，删除/替换会**静默失效**。为此新增 `name_bidx` 列
（HMAC-SHA256 盲索引，确定性），等值查询走它。`delete_region()` 与保存时的"先删后插"
都依赖这一列。

> 代价说明：盲索引是确定性的，会泄露"两行的明文是否相同"这一个 bit。
> 这是所有可搜索加密方案的固有代价（Django `django-cryptography`、
> DynamoDB 加密客户端同理），但不泄露明文本身。对短且低熵的区域名这个取舍是划算的 ——
> 反正也保护不了"是否叫这个名字"，而删除功能坏掉是立刻可见的产品缺陷。

**验证**

- `tools/test_field_crypto.py`（39 项）：在真实库副本上验落盘是密文、应用层读回是明文、
  数据零丢失、迁移幂等、新增/更新/反馈/区域 CRUD 全走加密、坏密文降级不拖垮列表。
- `tools/demo_doctor.py` 的 `L7 业务数据加密`：每次演示前自检"到底加没加密"。
- 回归：`regress_all.sh` 306/306 通过（含 `test_isolation.py` 83 项）。
- HTTP 层额外验证 15/15：接口返回的 `region`/`code` 是明文、响应不含 `ENC1:` 痕迹、
  `DELETE /api/regions/{name}` 可用（盲索引路径打通）、报告导出正常。

> ⚠ **密钥必须单独备份**：`.data_key` 丢失 = 库里所有密文永久无法解密。
> 已备份至 `backend/data/backup/data_key_backup_20260920.txt`，并**实测该备份能解密真实数据**。
> 部署到新机器时，除了 `.env` 还要带上这个密钥文件（或改用 `WB_DATA_KEY` 注入）。
