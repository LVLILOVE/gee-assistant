# 卫星遥感影像智能分析助手 · 部署手册

本手册指导在 Windows 环境下从零部署本项目，覆盖后端、前端、生产模式与对外发布。

## 1. 环境要求

| 项 | 要求 | 本项目实测 |
|---|---|---|
| 操作系统 | Windows 10/11 | Windows 10 |
| Python | 3.12+（干净 venv） | 3.13.14（托管 Python 建 venv） |
| Node.js | 18+ | 22.22.2 |
| npm | 9+ | 10 |
| 网络 | 国内可访问 DeepSeek API | ✅ 直连 |

> ⚠️ 本机 conda 的 Python 3.12 存在 pip/ensurepip 损坏问题，建议使用系统 Python 3.12+ 或托管 Python 创建 venv（见 2.1）。

## 2. 后端部署

### 2.1 创建虚拟环境

```bash
cd gee-assistant/backend
python -m venv .venv          # 用可用的 Python 3.12+ 解释器
.venv/Scripts/python.exe -m pip install --upgrade pip -i https://pypi.tuna.tsinghua.edu.cn/simple
```

### 2.2 安装依赖（清华源）

```bash
.venv/Scripts/python.exe -m pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

主要依赖：fastapi、uvicorn、httpx、langgraph、pydantic、python-dotenv、numpy、pandas 等。

### 2.4 首次启动必须做的两件事（安全）

服务一旦通过 cpolar 暴露到公网，就等于把这台机器上的 **DeepSeek 与 Earth Engine 额度**
开放给了任何知道 URL 的人。因此首启必须处理访问控制，二选一：

**方式 A：预置管理员（推荐，确定性最强）**

在 `.env` 里填好你自己的账号（密码至少 8 位）：

```ini
ADMIN_USERNAME=your_name
ADMIN_PASSWORD=<你自己的强密码>
```

重启后端，日志里会出现：

```
[auth] 预置管理员 'your_name' -> created
```

直接用这个账号登录即可。该操作**幂等**——已存在就跳过，不会重置密码。

**方式 B：页面自助注册**

打开首页 → 切到「注册」→ 填写用户名（3–32 位）与密码（至少 8 位）。
**注意**：不预置时，**第一个注册的用户自动成为管理员**——服务在公网时，
谁先访问谁就能拿到管理员。所以用这种方式请**立即注册**，注册完把
`ALLOW_REGISTRATION=false` 写进 `.env` 并重启，关掉公网注册入口。

> 两种方式都建议：登录后在页面右上角用「修改密码」把密码换成自己记得住的。
> 修改成功后所有会话会立即失效，需要用新密码重新登录。

**从旧版本升级（老库自动迁移）**

若之前跑过没有登录的版本，`data/app.db` 里已经有历史任务，**不需要手工改库**：
启动时会自动

1. 给 `tasks` / `regions` 补 `user_id` 列；
2. **把 `regions` 的主键从 `name` 单列重建为 `(name, user_id)`** ——
   旧结构下 `INSERT OR REPLACE` 会让「别人保存同名区域」直接顶掉你的那一行，
   这是跨用户数据破坏，必须重建表才能修（主键无法 `ALTER`）；
3. 把 `user_settings` 重建为 `(key, user_id)` 联合主键；
4. 把残留的 `NULL` 归属归一成 `0`（`0` = 无主 / 全局默认值）。

老数据**一条不丢**，设置值原样保留为全局默认值，区域坐标不变。

紧接着，**首个管理员一旦产生**（预置或注册），历史任务与区域会一次性划归其名下，日志会打印：

```
[数据归属] 已把 22 条历史任务划归管理员（user_id=1）
```

这一步幂等且只动 `user_id = 0` 的行，重启不会重复执行。之后每个新注册用户
看到的历史列表都是空的 —— 他们看不到升级前那批数据，这正是隔离生效的表现。

> ⚠ 迁移是**单向**的（老代码读不了新结构）。升级前先把 `data/app.db` 备份一份。

### 2.5 公网还有四道必须收紧的口子

登录只挡住了「没账号的人」。下面四项是给「已经注册了的账号」「恶意网页」
「直接构造 URL 的陌生人」和「被诱导的生成代码」准备的。

**① 任务配额（`MAX_CONCURRENT_TASKS*` / `TASK_RATE_LIMIT_*`）**

`ALLOW_REGISTRATION=true` 时任何人注册一个号就能无限提交任务，而每条任务都要烧
DeepSeek token 并占用 GEE 云端算力。所以提交口设了四层额度：

| 维度 | 默认 | 触发时的响应 |
|---|---|---|
| 全局并发 | 3 | `429` + `Retry-After: 30` |
| 单用户并发 | 2 | `429` + `Retry-After: 30` |
| 单用户每小时 | 20 | `429` + `Retry-After: 3600` |
| 单用户每天 | 60 | `429` + `Retry-After: 86400` |

几个设计要点：

- **计数直接查库**，不用内存计数器 —— 重启服务不会把已用额度清零，重新部署也绕不过。
- **校验与建任务在同一把锁里**（`_submit_lock`）。分开写会让两个并发提交同时读到
  "还差一个名额"然后都放行，配额形同虚设。
- **重启时清理僵尸任务**：上个进程留下的 `pending`/`running` 会被标记为失败并写日志
  （`服务重启`）。不清的话它们既让前端一直转圈，又**永久占住并发名额**，
  用户再也提交不了新任务。

前端提交失败时会直接显示后端给的 `detail` 文案（如"已达单用户并发上限（2），
请等待当前任务完成"），不是笼统的 "Request failed with status code 429"。

**② CORS 来源白名单**

曾经的配置是 `allow_origins=["*"]` + `allow_credentials=True`。实测（`curl -H "Origin: https://evil.example.com"`）
**任意 Origin 都会被原样回显**，并带上 `Access-Control-Allow-Credentials: true` ——
等于告诉浏览器「任何网站都可以带着用户的 cookie 读这个接口」。

当时没被打穿，靠的是会话 Cookie 的 `SameSite=Lax`（跨站 `fetch` 不带 cookie）。
但只要哪天为了支持独立前端把 Cookie 改成 `SameSite=None`，它立刻变成
「任意网站可读取你的全部任务列表」的漏洞。

**生产环境前端由本服务同源托管，根本不需要 CORS**，所以现在改成白名单：
默认只放行 Vite 开发端口（`localhost:5173` / `127.0.0.1:5173`），
要加来源写 `CORS_ORIGINS`。`tools/test_auth_http.sh` 第 12 组会断言
「陌生 Origin 不被回显」，防的就是这个回归。

**③ 静态托管不能让路径穿出去（这一条踩过，必须看）**

生产模式是单端口，前端 `dist/` 由后端托管，因此有一条 SPA 兜底路由，把没匹配上的
GET 回退到 `index.html`（支持前端单页路由）。它曾经长这样：

```python
@app.get("/{full_path:path}")
def spa(full_path: str):
    candidate = FRONTEND_DIST / full_path      # full_path 直接来自 URL
    if candidate.is_file():                    # ← 没有"必须还在 dist 里"的判断
        return FileResponse(candidate)
    return FileResponse(FRONTEND_DIST / "index.html")
```

`%2e` 是 `.` 的合法编码，uvicorn 在构造请求对象**之前**就把它解码了，于是

```bash
curl --path-as-is "http://127.0.0.1:8010/%2e%2e/%2e%2e/backend/.env"
```

进入路由时 `full_path` 就是 `../../backend/.env`，与 `FRONTEND_DIST` 拼接后指向
`dist/` 之外，而 `is_file()` 照样为真。**这条路由没有任何鉴权**，结果：

| 能读到 | 实测 |
|---|---|
| `backend/app/*.py` | 200 · `text/x-python` · 5435 B |
| `backend/.env` | 200 · `application/octet-stream` · 2717 B（含 `DEEPSEEK_API_KEY`） |
| `backend/data/app.db` | 200 · `application/octet-stream` · 233472 B（用户 / 密码哈希 / 会话 / 任务） |

而且**公网上同样打得通**：修复后重发同一请求，服务端日志记到
`14.19.47.224:0 - "GET /../../backend/.env HTTP/1.1" 404` —— 路径里的 `..`
原样穿过 cpolar 到达了应用。

现在的写法（`backend/app/main.py`）：

```python
def _safe_dist_file(full_path: str):
    dist_root = FRONTEND_DIST.resolve()
    candidate = (FRONTEND_DIST / full_path).resolve()   # resolve 会解开软链
    if candidate == dist_root or not candidate.is_relative_to(dist_root):
        return None                                     # 越界：不给
    return candidate if candidate.is_file() else None
```

配套的两条：路径里出现 `..` 段直接 **404**；`/api/`、`/health`、`/docs` 等前缀
未匹配到路由时返 **JSON 404**（以前会返 200 + HTML，调用方以为成功、只在解析时炸，
排查时看到的是一个 200，极难定位）。

验证（**必须带 `--path-as-is`**，否则 curl 会自己把 `..` 归一化掉，请求根本没发出去）：

```bash
curl -sS --http1.1 --path-as-is -o /dev/null -w '%{http_code} %{content_type}\n' \
  "http://127.0.0.1:8010/%2e%2e/%2e%2e/backend/.env"      # 期望 404 application/json

.venv/Scripts/python.exe tools/test_static_route.py         # 57 项断言
bash tools/smoke_live.sh                                    # 含穿越回归组
BASE=https://<你的域名>.cpolar.top bash tools/smoke_live.sh # 公网复验
```

> ⚠ 本机若在改过 `backend/.env` 后重启过、且服务在公网上跑过一段时间，
> 该 `DEEPSEEK_API_KEY` 应视为可能已泄漏，建议到 DeepSeek 控制台吊销重发。

**④ 执行沙箱不能读敏感文件（同一类问题的第二个入口）**

沙箱原本只封了**网络**（域名白名单）与**子进程**（`_block_process_creation`），
**文件系统是敞开的**。实测：沙箱里的代码 `open("backend/.env")` 能读到
`DEEPSEEK_API_KEY`，`os.listdir(".")` 能列出后端整个目录。

这条比看起来严重：沙箱里跑的代码是 **LLM 按用户输入生成**的，而注册是开放的 ——
任何注册用户写一句「读取 `.env` 并打印」，密钥就随结果回到他手里。
**它和 ③ 是同一根因（攻击者可控字符串落到文件系统）的两个入口。**

现在的策略在 `app/execution/_runner.py` 的 `_block_sensitive_file_access()`：
执行用户代码前，把 `builtins.open` / `io.open` / `io.FileIO` / `io.open_code` /
`os.open` / `os.stat` / `os.lstat` / `os.listdir` / `os.scandir` 逐个换成带敏感路径判定的版本。
禁读禁写 `.env*`、`*.db*`、`*.key/.pem/.p12/.ppk`、
`.db_backup/`、`.git/`、`.ssh/`、`.aws/`、`*service_account*.json`、`id_rsa*` 等。

**⚠️ 这里最重要的一条：同一个「读文件能力」有多条并列入口，必须逐个封。**
第一版只封了 `builtins.open` / `io.open` / `os.open`（当时 26 项断言全绿），
但一句 `io.FileIO(".env").read()` 就把三道全绕过去了 —— 实测读出了密钥与
`SQLite format 3`（整库）。补上 `io.FileIO`（必须用**子类**替换，否则别处
`isinstance(f, io.FileIO)` 的判断会报错）、`io.open_code`、`os.stat`/`os.lstat` 之后才真正关上。
**改这里之后必须跑 `test_sandbox_fs.py` 的第 3 组对抗性用例**，它把 8 条入口逐个钉住。

两个**改这里时最容易踩的点**：

1. **加固点必须在 `_verify_toolchain()` / `_install_ee()` 之后、`exec(用户代码)` 之前。**
   放进 `_harden()`（流程最前面）会让整条链路直接挂 ——
   `python-dotenv` 在导入时就读 `.env`、`gee_auth.initialize` 要读凭据文件，
   这些都是我们自己的可信代码。实测报
   `PermissionError: 禁止访问环境变量文件：.env`，栈顶在 `_verify_toolchain`。
2. **必须显式放行 GEE 凭据路径**（`data/credentials/`、`~/.config/earthengine`，
   以及 `GEE_SERVICE_ACCOUNT_JSON` 等环境变量指向的**确切文件**）——
   后者可以指向任意位置任意文件名（例如 `D:\keys\my.json`），只靠目录片段放行不够。

验证：

```bash
.venv/Scripts/python.exe tools/test_sandbox_fs.py          # 35 项
.venv/Scripts/python.exe tools/gee_doctor.py --self-test   # 7 项（含"敏感文件禁读"探测）
```

> 注意 `tools/gee_doctor.py --self-test` 是本项目自己的防误伤闸门：
> 沙箱的黑名单/封禁是按「危险程度」挑的，而 stdlib 内部互相 import，
> 很容易连带打死自己，且只在真实执行时暴露。**改沙箱后必须跑它。**


> 这个脚本断言的不是「默认日期等于几」，而是**「默认日期是否随当天推算」**。
> 它今天能过、明年也能过，但谁要是再把年份写回代码里就立刻失败。
> 它用 `ast` 解析而不是正则搜文本，所以注释和文档里提到历史日期不会误报。

```bash
.venv/Scripts/python.exe tools/eval_metrics.py --self-test   # 11 项，纯离线，先跑这个
.venv/Scripts/python.exe tools/eval_metrics.py --intent-only # 只跑指标一（快，不消耗 GEE 配额）
.venv/Scripts/python.exe tools/eval_metrics.py               # 全量四个指标，约 10 分钟
```

> ⚠ 全量评测一次提交 8 个真实 GEE 任务，而 `TASK_RATE_LIMIT_PER_HOUR=20` ——
> **连续跑两遍必然撞 429**。runner 会自动读 `Retry-After` 等待重试（默认最多等 30 分钟），
> 并把「提交被拒/超时」这类**测量基础设施问题**排除出分母，不与「任务真的失败」混为一谈。
> 跑完会在 `docs/评测报告-<日期>.md` 生成报告。
>
> 想快速冒烟、验证四个指标能跑通，加 `--limit 2` 只跑前 2 条端到端任务。

失败任务复现（需要时）：

```bash
.venv/Scripts/python.exe tools/replay_task.py --last-failed  # 重跑库里最后一次失败的代码
```

> 它读的是**当时真正跑过的那份代码**（从库里取 `code` 字段），不是在本地重新生成，
> 所以能复现出用户当时看到的那次失败。注意「能复现」不等于「产品现在还失败」。

> `smoke_live.sh` 是**严格只读**的（不注册、不登录、不写库），所以它对生产实例
> 是安全的，可以随时跑。会写库的 `test_*_http.sh` 与 `eval_metrics.py` 一律自起
> 临时实例 + 临时库，或显式指向本地调试实例。

## 5. 对外发布（cpolar）

### 5.1 安装并登录 cpolar

从 [cpolar 官网](https://www.cpolar.com) 下载，运行 `cpolar authtoken <你的token>` 完成登录。

### 5.2 映射后端端口

```bash
cpolar http 8010 -region cn_top
```

输出形如 `https://xxxx.r31.cpolar.top` 的公网地址，外网可直接访问。

> 免费版每次重启子域名会变化；需要固定域名可在 cpolar 官网升级。
> **对外分享前先确认当前地址**：重启隧道后旧链接立即 404，
> 但本机 `:8010` 不受影响。查当前地址：

```bash
# 从 cpolar 日志里取当前公网地址
grep -oE "https://[a-z0-9]+\.r[0-9]+\.cpolar\.(top|cn)" <cpolar日志> | sort -u
```

### 5.3 隧道会自己死掉（实测过一次）

2026-09-17 早上发现公网访问 404，而本机 `:8010` 一直健康。cpolar 日志显示：

```
level=error msg="tunnelServerModel.Init error ... lookup cpolard.r31.cpolar.top: no such host"
...
level=error msg="WatchDog timeout, restart worker cpolar"
```

**不是本地服务的问题，是 cpolar 侧的 DNS 抖动**：

- 同期用 `nslookup cpolard.r31.cpolar.top` 是能解析的（`47.242.81.181`），
  但首次查询超时 2 秒才成功 —— 本地 DNS 明显不稳；
- cpolar 的 Go 解析器等不及就报 `no such host`，**而且之后只维持控制连接的心跳、
  不再重试隧道连接**，进程看着"活着"其实隧道早没了。

处理办法就是**重启 cpolar**（`taskkill /F /PID <pid>` 后重新执行 5.2 的命令）：

```bash
MSYS_NO_PATHCONV=1 taskkill /F /PID <cpolar的PID>
cpolar http 8010 -region cn_top
```

重启后**子域名会变**（本次从 `19f0a78b` 变成 `792ed623`），
所以对外发过的链接要重新发。判断是否恢复看日志里有没有这两行：

```
[:tunnel server module] Tunnel established at https://xxxx.r31.cpolar.top
```

再验证三个端点：`/health` 200、`/api/regions` 200、`/api/tasks` 401。

> 用 `curl` 测 tunnel 后的站点时加 `--http1.1`，并把 `-o` 指到真实可写路径。
> 实测直接 `-o /dev/null` 会偶发 `curl: (23) client returned ERROR on write`，
> 输出 `%{http_code}=000` 的假失败。

### 5.4 同一个 DNS 缺陷的彻底绕法：写 hosts（2026-09-23 实测）

5.3 的"重启就好"只是治标 —— 2026-09-23 又复发，而且这次连
`WatchDog` 都没救回来，日志里反复出现：

```
level=error msg="[pxy:pxy:20a067a0] Server failed to read StartProxy:
    read tcp 192.168.110.181:51980->47.242.81.181:4443: i/o timeout"
```

**关键判据：控制通道还在活（日志里 `Ping`/`Pong` 正常），只有数据通道超时。**
所以"进程在不在"完全不能说明隧道通不通。

定位过程中确认了这不是网络问题，而是 **cpolar 客户端的解析缺陷**：

| 检查项 | 结果 |
| --- | --- |
| `nslookup cpolard.r31.cpolar.top` | ✅ `47.242.81.181` |
| Python `socket.gethostbyname` | ✅ `47.242.81.181` |
| TCP 直连 `47.242.81.181:4443` | ✅ 可连 |
| **cpolar 自己的 Go 解析器** | ❌ `no such host` |

处理办法：把隧道服务端**静态映射进系统 hosts**，让 cpolar 不必自己解析。

```
# C:\Windows\System32\drivers\etc\hosts
47.242.81.181 cpolard.r31.cpolar.top
```

改完 `ipconfig /flushdns`，再重启 cpolar，隧道立刻建立。

> ⚠️ 这是**系统级修改**，动之前先备份 hosts（本次备份为 `hosts.bak_20260923`）。
> 不需要时把该行删掉即可恢复原状。
> 另外注意：hosts 只需映射**隧道服务端** `cpolard.r31.cpolar.top`；
> 公网访问域名（如 `xxxxx.r31.cpolar.top`）走正常 DNS 即可，
> 实测它同样解析到 `47.242.81.181`，**不要**再手工加一条。

### 5.5 免费隧道的真实可用度（别对外承诺"稳定"）

关掉 hosts 缺陷后，2026-09-23 实测公网 `/health` 连续 10 次：

```
200|0.44s   000|21.07s   200|3.46s   200|0.17s   200|0.13s
200|0.13s   200|0.13s    200|0.09s   200|0.10s   200|16.68s
```

即 **成功 9/10，但尾延迟可达 16~21 秒**，而且失败那一次直接超时。
同刻本地直连 `:8010` 是 **稳定 6ms**。

**结论**：免费隧道可以给演示用（一次性打开页面、跑一个任务通常没问题），
但**不能承诺"随时稳定可访问"**。给评审看的场合，建议提前打开页面、
或现场用本机 `:8010` 直连作主路径，公网链接只作为"外网可访问"的证明。

## 6. 常见问题 FAQ

**Q1：conda 环境 `python -m venv` 报 ensurepip 错误？**
A：本机 conda Python 的 pip 已损坏。改用系统 Python 3.12+ 或托管 Python 创建 venv。

**Q2：`pip install` 下载慢或失败？**
A：使用清华源 `-i https://pypi.tuna.tsinghua.edu.cn/simple`。

**Q3：`npm install` 慢？**
A：使用 npmmirror 源 `--registry=https://registry.npmmirror.com`。

**Q4：后端端口 8010 被占用？**
A：`.env` 中改 `BACKEND_PORT`，并同步修改 `frontend/vite.config.js` 的代理目标。

**Q5：没配 DeepSeek key，能跑吗？**
A：能。代码生成降级为内置模板、意图解析降级为关键词规则，系统仍可离线演示。

**Q6：外网访问 cpolar 地址首次弹提示页？**
A：cpolar 免费版特性，点击「继续访问」即可。

**Q7：真实 GEE 执行怎么开启？**
A：**当前已在用**（2026-09-16）：项目 `weixing-508708` + 个人 OAuth 凭据，
`EXECUTION_BACKEND=gee`，太湖流域 NDVI 与洞庭湖水体提取均已真实跑通。
若要在新机器复现，三步：① 按 [GEE凭据配置指南.md](./GEE凭据配置指南.md) 创建并导入凭据
（`.venv\Scripts\python.exe tools\gee_doctor.py --oauth`，或 `--import-sa "key.json"` 自动加密落盘）；
② 在 `.env` 填 `GEE_PROJECT` 与（必要时）`GEE_PROXY`；
③ `tools/gee_doctor.py --set-project 你的项目ID` 校验通过后会自动改写
`GEE_PROJECT` + `EXECUTION_BACKEND=gee`，重启即生效。
未就绪时可随时切回 `offline` 用离线样例兜底——这是任务书 6.3 明确允许的形态。

**Q8：为什么我在电脑里找不到 GEE 凭据文件？**
A：因为凭据不会自动生成，必须由你在 Google Cloud Console 创建服务账号并下载 JSON 密钥
（或本地执行 `earthengine authenticate` 走个人 OAuth）。详见配置指南第 2、3 节。

**Q9：`/api/gee/status` 返回什么？**
A：GEE 接入诊断：依赖是否安装、凭据来源、账号（脱敏）、项目 ID、出网代理、鉴权是否通过、下一步怎么做。
页面右上角「GEE · 查看」标签点开就是这个信息，凭据未配置时会直接给出补配置的命令。

**Q10：GEE 请求走什么网络？会不会影响其它功能？**
A：只走 `GEE_PROXY` 指定的代理，且**强制覆盖**进程内的 `http_proxy`/`https_proxy`
（宿主环境注入的代理对 TLS 隧道会返回 502，会让 GEE 静默失败）。
本机实测：直连 Google 不通，走 `GEE_PROXY=http://127.0.0.1:7897` 后
`earthengine.googleapis.com` 与 `earthengine-highvolume.googleapis.com` 均返回 200。
换网络工具后运行 `tools/gee_doctor.py --detect-proxy` 可自动重新发现端口。

**Q11：怎么确认凭据与链路真的通？**
A：两条命令，都不依赖大模型：
① `.venv\Scripts\python.exe tools\gee_doctor.py --set-project <项目ID>`
—— 真实 `ee.Initialize` + 数据集调用，**验证通过才写回配置**；
② `.venv\Scripts\python.exe tools\verify_real_gee.py 太湖流域`
—— 在真实子进程沙箱里跑一遍完整任务（退出码 0=通过 / 1=链路失败 / 2=曲线大量缺失）。
最硬的证据是图层瓦片 URL 里带着项目 ID：`.../v1/projects/<项目ID>/maps/...`。

**Q12：地图面板空白，或只有底图没有数据？**
A：两个原因，都已修复：
① 前端此前**只渲染 geojson**，而真实 GEE 返回的栅格图层是 `tile_url`（瓦片模板）
—— `MapPanel` 已支持；纯瓦片图层没有 geojson 算不出视野，已由任务详情里的 `region` 兜底定位；
② 浏览器直连 `earthengine-highvolume.googleapis.com`（GEE 栅格）与
`tile.openstreetmap.org`（底图）**都是 HTTP 000**，TCP 层就失败 —— 两者都必须走后端代理
`/api/tile/{z}/{x}/{y}?u=` 与 `/api/basemap/{z}/{x}/{y}`。
因此**前端不需要能访问外网**，本地与 cpolar 公网场景都成立。
若瓦片接口偶发 502，是代理节点抖动，换节点即可（逐张瓦片失败 Leaflet 会自己重试）。
